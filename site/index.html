A method and a plugin for Claude Code and Codex

A method for working with AI agents, so you get what you had in mind.

ProjectStore is a method and a framework for building apps and services of any size with AI agents.

First of all, it is a way for a person and agents to work together. You decide what to build. An agent writes the plan, a second agent looks for holes in it, and you approve. Then the agent builds, and a third checks the result against your checklist, item by item.

It installs as a plugin in Claude Code and Codex. From then on you talk to the agent in your own words, and it keeps the decisions, plans and progress as plain files in your project. Tomorrow, on another machine or in another agent, the work picks up where it stopped.

Why it works
  • The reviewer won’t close the task until every point of the checklist is checked.
  • The session starts from the task board and the story in progress.
  • The decision is written down with its reason, and the agent follows it.
  • Codex reads the same files and carries on.
  • Every decision has a file with the reason and the options you turned down.

Install and first steps

You can start even if you are not a programmer.

Your agent runs the commands for you. You install two programs, open a project folder and paste one sentence.

Quick start

  1. Get an agent

    An agent is a program that writes and runs code from your words. Either works: Claude (the app, its Code tab) or Codex by OpenAI.

  2. Install Node.js and open a project folder

    Node.js is what ProjectStore runs on: the LTS installer from nodejs.org, version 20 or newer, on macOS or Linux. Make an empty folder, say “my-bot”, and open it in the agent.

  3. Install ProjectStore

    Ask your agent or run the command in a terminal in the project folder.

    Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.
    ~/your-project $
    npx projectstore setup

    After installing, restart the agent; Codex asks once to approve its hooks.

  4. Say what you want to build

    I want to create a stock trading bot

  5. Answer its questions

    The agent asks what only you can decide, before it plans:

    The project is empty—no code, and the vault just has README scaffolding with no epics, stories, or ADRs yet. Per CLAUDE.md, I'll start with an epic and its stories in the vault rather than code, but first I need you to make a few decisions that will shape the plan.

    Should the bot trade real money?

    1. Paper only (Recommended) · paper/sandbox account
    2. Backtest only · historical data, no broker
    3. Live, with safeguards · kill switch, position limits, daily loss cap

    From a real Claude Code session on an empty project, 21 October 2026. The agent's text is quoted word for word; the option details are shortened.

  6. Approve the plan

    The critic has checked it by then. After your yes, the agent builds it, and the reviewer checks the result against the checklist.

How it works

A loop with an independent check in it.

Agents write code fast, and they re-decide settled questions just as fast: every fresh session arrives empty. The fix is not a smarter agent. It is gather context → act → verify, run over the project and not only over the code.

The agents

6 agents. All but one may only read.

The advisors check, plan and tidy up, and change nothing. One clerk saves only what you approved, after your Yes.

criticread-only · independent

After an ADR, spec, epic, story or design is written or changed

Looks for weak spots, checks every claim against the source and asks how the plan could fail. No flattery.

opus · max
plannerread-only · independent

Before work on a story starts (story plan)

Looks at where earlier epics live in the code. Says where the change belongs, what to reuse, what to watch out for and in what order to work.

opus · max
reviewerread-only · independent

After code, before commit or story close

Asks for proof on every acceptance criterion, including the spec's. Then checks correctness, regressions and tests.

opus · max
librarianread-only · suggests

From time to time, before releases, after the vault grows fast

Finds what no rule can catch: research notes that contradict an accepted ADR, duplicates, missing links, files ready to archive.

opus · max
archaeologistread-only · suggests

Once, after binding an existing codebase

Finds decisions nobody wrote down, in the code, config files and git history. Suggests ADRs for them, with evidence.

opus · max
clerkwrites · after your Yes

Only inside a command flow, only after your Yes

Saves exactly what you approved, nothing more. Then rebuilds the board and runs the checks. Writes nothing of its own and asks nothing.

sonnet · max

The default models are Claude Code's. In Codex each role is a skill of the same name that asks Codex to start the role, such as $projectstore-critic for the critic; it uses the session's model unless you set one.

The guards

Mechanisms hold it together, not discipline.

No story, a nudge

An agent that starts editing code with no story open is reminded to open one. A feature-sized change starts in the vault.

Unreviewed stays marked

An artifact that needs review carries review_status: pending until a critic pass is applied. "Not yet reviewed" is a state the tools can read, not something someone must remember.

A doctor with no AI in it

doctor checks the vault's mechanical consistency deterministically. In CI it runs with no agent and no tokens.

Where to look, generated

graph.md holds every artifact's links in both directions; code-map.md says where each epic's code lives. Before an architectural choice, the agent is pointed at the ADR index first.

After /compact, the vault comes back

In Claude Code, after a /compact you run, the session starts with the vault's orientation again, and with the vault files the conversation touched before it.

A second session is warned

A session that starts while another one works on the same vault opens with a multi-session warning: search before creating anything new.

Done means proven

A story closes with evidence under each criterion.

The planner said where the change belongs before the code, and the plan went into the story on your yes; the reviewer checked the diff against each criterion after it. Each line of proof is a test, a command that ran, or a line of code.

Any agent can read this record, with or without the plugin: through the CLI, which answers with JSON and needs no tokens, or through the MCP server's 8 read-only tools.

Fine print

Fine print

  • Running the loop costs tokens: the drafts, the critic and the reviewer run on the model you already pay for. The README measures it.
  • The critic and the reviewer are separate agents with a fresh context in Claude Code. In Codex the roles are skills.
  • ProjectStore is shared project context and a way of working. It is not an agent orchestrator: launching agents is your harness's job.
Team and many sessions

Many sessions. Many people. One vault.

The context belongs to the team, not to one developer's chat. ADRs and specs go through pull requests, like code. What gets reviewed is the reasoning.

Four ways to work

Four ways to work

Several sessions, one vault

Two agents or two people in one vault at the same time is normal. Each session knows about the others, and a few simple rules keep them out of each other's way.

  • No silent overwrites. Before saving a new file, ProjectStore checks that it does not exist yet. Two sessions on the same topic get a clash, not two copies.
  • Each status line shows its own work. 2–6 sessions side by side each see exactly their own epic and story.
  • Session names are offered, not imposed. Once a session settles on one piece of work, it suggests a name for it. Rarely: at most twice a session, 12 offers across nine recorded sessions.

Everyone sees more than their own part.

The developer, the tech lead and QA work from the same decisions and criteria. A person without an agent needs only GitHub or a Markdown editor: it is just files.

The context is available to the whole team, not only to the owner of the chat.

Shared contracts. Separate areas of work.

In one project, the API, Web and Platform teams run their own epics on top of shared ADRs and specs. A change to a shared contract is discussed in review with the teams that use it. ProjectStore shows which stories depend on it.

Who owns which artifacts and who signs off on contracts is the team's call.

Different executors. Shared grounds.

The planner reads the decisions and the code map. The implementer reads the story and the spec. The reviewer reads the diff and the criteria. Each gets the context it needs, not the whole history of someone else's session. Sessions on the same vault warn each other.

Launching agents and handing work between them is the job of your harness or orchestrator.

Why it works

The industry invented this long ago.
Agents made it cheap.

ADRs, reviews, a backlog, acceptance criteria, links from goal to code. Mature engineering teams have worked this way for twenty years. ProjectStore invents none of it.

Where each piece comes from

Where each piece comes from

  1. 1969RFCs: decisions written down and numbered, then discussed in the open.
  2. 1992DO-178B: in avionics, every requirement must trace to code and to a test.
  3. 1995Scrum: the work as a backlog, ordered and visible.
  4. 1999XP: user stories, and acceptance criteria that say when one is done.
  5. 2007Kanban for software: a board that shows what is in flight.
  6. 2011ADRs, Michael Nygard: one short file per architectural decision.
  7. nowCoding agents: every step takes minutes. Without the artifacts, every session starts empty.
The expensive part

The process was always valuable. What was expensive was people running every step of it.

people's process+agents' speed=ProjectStore

ProjectStore puts the two together. Agent speed makes the old process cheap for the first time. Its documents, kept in files beside the code, give agents what they never had: the project's context, linked up to the goals and down to the code. A second agent that did not write the draft reviews each step, by rule. Speed gets a memory, and memory gets a check.
