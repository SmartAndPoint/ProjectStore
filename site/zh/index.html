01 / 原则

不必再解释一遍。
从上次停下的地方继续。

聊天记得的是你们聊过什么。ProjectStore 记录的是团队决定了什么、为什么这样决定、怎样检查结果。下一个智能体、下一个模型，或者六个月后的你，读到的是带日期的决策和被否决的方案，而不是聊天记录。

为什么为什么这样选？决策及其备选方案，记录在 ADR 中。
做什么我们在做什么？一份 spec、一个 epic，以及标准明确的 story。
证明是如何验证的？评审，以及每条标准对应的证据。
02 / 为何有效

这一套，行业早就发明了。
智能体让它不再昂贵。

ADR、评审、待办池、验收标准、从目标到代码的关联。成熟的工程团队这样工作已有二十年。这些都不是 ProjectStore 发明的。

看看任何一个成熟的工程团队。动手之前，先有人把决策写下来，其他人一起讨论。工作被拆成 story，放进待办池。每个 story 都有验收标准。每条需求都能追溯到代码。待办池来自 1995 年的 Scrum。story 和验收测试来自 1999 年的 XP。ADR 是记录一项决策及其理由的简短文档，由 Michael Nygard 在 2011 年提出。设计评审和 RFC 还要更早。

这套流程是有效的。项目结束后，它留下的文档是公司最有价值的资产：系统为什么这样构建，什么才算完成，每个功能在代码的什么位置。但靠人手工推进时，它很慢。写一份 ADR 要一个下午，等评审要一周。文档跟不上代码。看板和实际情况对不上。于是团队在流程上能省就省，“敏捷”成了什么都不写的借口。

流程一直都有价值。昂贵的是每一步都要由人来执行。

智能体正好相反。写一份 ADR、把 epic 拆成 story、对照标准检查 diff，智能体只需几分钟，而不是几天。智能体缺的，恰恰是人天然就有的东西：会话之间的记忆、与同事共享的上下文、从目标到代码的关联。每个新会话都从空白开始，把早已定下的事再决定一遍。

ProjectStore 把两者结合起来。智能体的速度第一次让这套老流程的成本降了下来。流程留下的文档以文件形式放在代码旁边，给了智能体从未有过的东西：项目的上下文，向上连到目标，向下连到代码。每一步都由另一个没有参与写草稿的智能体检查。速度有了记忆，记忆有了检查。

决策为什么
ADR（架构决策记录），Michael Nygard，2011 年。在此之前是架构委员会和设计评审。
写要一个下午，在评审队列里排一周。被否决的备选方案只留在某个人的脑子里。
智能体一分钟写出草稿，独立的 critic 找出其中的弱点，再由你批准。结果是一个带日期的文件，被否决的方案也记在里面。
契约怎么做
Spec、设计文档、RFC。RFC 自 1969 年起就有编号；设计文档在大公司是标配。
写要一周，到发布时已经过时。没人检查代码是否仍与之相符。
spec 用带编号的规则写明预期行为。它的检查项适用于它覆盖的每个 story。spec 还是草稿时，story 无法关闭。
待办池做什么
产品待办列表，Scrum，1995 年。用户故事，XP，1999 年。用于软件开发的看板，2007 年。
待办池梳理会。看板靠手工维护，不出一周就与现实脱节。
每个 story 文件自己记录状态。看板、索引和关系图都由这些文件生成。一旦对不上，一条命令就能重建。
计划改哪里
技术设计、影响分析。技术负责人判断改动会落在现有代码的哪个位置。
早先的功能是怎样落到代码里的，这些知识只存在于技术负责人的脑子里。而他正在休假。
planner 查看早先的 epic 落在代码的哪些位置，指出改动应该放在哪里、复用什么。计划写进 story。
验收证明
验收标准、完成的定义（Definition of Done）。XP 和 Scrum，2000 年代初。
冲刺末尾的一轮 QA。“完成”靠宣布；标准只做抽查。
reviewer 拿 diff 对照每一条标准，并要求证据：一个测试、一条运行过的命令、一行代码。没有证据，就不能关闭。
可追溯性关联
需求可追溯性。自 DO-178B（1992 年）起在航空电子领域是强制要求，在医疗软件中也是。
一张“需求 → 代码 → 测试”的 Excel 矩阵，第二个版本发布后就再没人更新。
每个 story 向上关联到它的 epic、ADR 和 spec，向下关联到它的代码。证据写在每条验收标准下方。关系图和代码地图是自动生成的，没人需要手工维护。

03 / 带验证的循环

先定依据。
再做实现。

不是一个“什么都做”的漫长会话。六个步骤，每一步都有结果、有检查。点击图中的节点或标签页。

先达成共识

写代码之前，先把任务写下来。

智能体先找出任务在项目中的位置。决策写成 ADR：一份简短的记录，说明选了什么、为什么。预期行为写成 spec，即代码必须遵守的规则。工作拆成 epic 和带验收标准的 story。在你说“是”之前，什么都不会保存。

有了一个可验证的任务，而不只是一段对话。

独立视角

趁改动成本还低，先检查决策。

critic 是一个没有参与撰写草稿的智能体。它专门找站不住脚的假设、遗漏的方案，以及计划可能失败的地方。它被明确告知：错误放行的代价是错误驳回的 10–100 倍。

风险在实现之前就成为决策的一部分。
projectstore:critic · 只读示例
需修订3 条意见
1. 备选方案：“MongoDB — 没有事务”从 4.0 起就不成立了。真正的原因
   是关系约束。要把这一点写明，否则这份 ADR 会误导下一位读者。
2. 影响：夜间对账任务怎么处理？移除还是保留？
3. 决策：“一个事务”包含什么？订单和明细行，不含支付。
   这条边界就是决策本身，却没有写下来。
智能体的结论不能代替你的批准。作者负责修改草稿，但从不批准自己的工作。
批准与待办池

批准。放进待办池。

修改完成后，你会看到文件路径和完整内容，然后说“是”。同一个“是”也会更新该文件夹的索引。epic 和 story 进入待办池。看板根据文件自动生成，没人需要手工维护。

没有你的“是”，什么都不会写入。

对照承诺的结果检查代码。

提醒

没有 story 就写代码，会收到提醒

没有进行中的 story，却改了三个或更多源文件，智能体就会收到一次提醒：先开一个 story。只统计实际发生的编辑。

先评审

未经评审，什么都不算定稿

每份新的 ADR、spec、epic 和研究笔记都会一直标着“未评审”，直到 critic 审视过为止。你的智能体指令里有一小段内容，确保新文档先经过 critic，之后才会被当作定稿。

doctor · 不用 AI

常规检查，不用 AI

看板和 story 是否一致？有没有失效的链接，或指向不存在代码的链接？有没有未开 story 就在进行的工作？它在会话开始时运行，只有出问题时才会出声。

↳ 决策与写入都要经过批准。独立的智能体协助检查；责任仍在团队。

04 / 留在磁盘上的内容

普通的文件。
格外有用的关联。

在编辑器里阅读，在合并请求里讨论，在 Obsidian 里打开。上下文不绑定任何一个工具。

ADR / markdown + yaml

不只保留选择，也保留理由。

ADR 记录一项架构决策：背景、备选方案、最终选择及其影响。决策推翻后，原来的 ADR 不会删除，而是指向取代它的那一份。六个月后，没人会把同样的争论再来一遍。

05 / 协同工作

一个项目。
不止一个参与者。

上下文属于团队，而不属于某个开发者的聊天。ADR 和 spec 像代码一样走合并请求。被评审的是推理过程。

每个人看到的都不只是自己那一部分。

开发者、技术负责人和 QA 基于同一套决策和标准工作。没有智能体的人只需要 GitHub 或一个 Markdown 编辑器，因为这些都只是普通文件。

整个团队都能用到这份上下文，而不只是发起聊天的那个人。

团队配置，分步说明

01

独立的 vault 仓库

每个项目一个项目文档仓库，而不是每人一个。它与代码仓库并列存放。

02

各自检出并绑定

每个人在自己的代码副本里运行 /projectstore:bind。这项设置只保存在本机，不会被提交。

03

分支加合并请求

每项决策在被接受之前，都要经过人工评审。critic 在合并请求之前审视它，你的团队在合并请求中评审它。

04

在 CI 中运行 doctor

npx projectstore doctor --json 在 CI 中运行，不需要智能体，也不消耗 token。发现问题时，它会让这一步失败。reconcile --write 也可以在 CI 中重建看板。

多个会话，同一个 vault

两个智能体或两个人同时在同一个 vault 中工作，是常态。每个会话都知道其他会话的存在，几条简单的规则让它们互不干扰。

  • 不会悄悄覆盖。保存新文件之前，ProjectStore 会检查它是否已经存在。两个会话写同一主题时，会得到一次冲突提示，而不是两份副本。
  • 每个状态栏只显示自己的工作。2–6 个会话并排运行，各自只看到属于自己的 epic 和 story。
  • 会话名称只是建议，不是强加。一旦会话的工作集中到某一项上，它就会建议一个名称。频率很低：每个会话最多两次，有记录的九个会话中共建议 12 次。

01

角色 做什么

规划、审视、写代码或检查结果。每个角色的分工都很清楚：顾问只读，clerk 只保存已批准的内容。

02

模型 用什么思考

按任务和预算来选。/projectstore:agents configure 为每个智能体单独设置模型。更换模型不会影响项目的历史。

在 GitHub 上讨论
这是一个记忆插件吗？

不是。记忆插件记住的是智能体说过什么。ProjectStore 记录的是项目决定了什么，形式是经过评审、带状态和日期的文档。之后的新工作都以这些文档为依据。换模型时差别就显现出来了：记忆属于模型，vault 属于项目。

它会取代 Jira、Linear 或其他任务跟踪工具吗？

不一定。ProjectStore 把决策、spec、story 和代码关联起来。你可以继续用原来的跟踪工具做计划，把技术上下文放在 vault 里。它不与其他跟踪工具自动同步，但 story 里可以保存指向对应工单的链接。

需要 Obsidian 吗？

不需要。vault 就是一个装着 Markdown 文件的普通文件夹。可以在编辑器里打开、在 GitHub 上浏览；如果喜欢 Obsidian 的关系图谱和看板，也可以用它。没有插件，这些文件照样可读。

它会不经询问就写入吗？

不会。每个新文件或每次编辑都会先展示给你，附上路径和完整内容，然后等待“是”“保存前编辑”或“否”。在一旁观察对话的辅助程序只会建议命令。唯一能写入的智能体 clerk 在你说“是”之后运行，一字不差地保存你批准的内容。

如果两个智能体修改同一个文件会怎样？

各自在单独的分支上工作，然后照常评审、解决 git 冲突。在同一个本地 vault 中，会话之间会互相提醒，新文件也绝不会被悄悄覆盖。但这不是锁，也不会在机器之间同步。

如果有人手工编辑 vault 文件呢？

允许，因为禁止从来都行不通。你会收到提醒，让你运行 reconcile。doctor 能发现与文件不再一致的看板或索引，reconcile 会根据源文件把它们重建。

项目上下文会流向哪里？

ProjectStore 不需要服务器：vault 放在哪里，就在哪里。智能体读取哪些文件、哪些内容会发送给模型提供商，取决于你的 harness 及其权限。不要把机密信息放进项目文档，并核对团队的访问规则。

检查是免费的吗？

不是。critic 和 reviewer 的运行会消耗你所用模型的预算：在 ProjectStore 自己的仓库上占总开销的 22.5%，一般占每周额度的 10–15%。常规检查 doctor 和 reconcile 不用 AI。按改动的风险决定流程的深度。

如果我们从 Claude Code 换到别的智能体呢？

什么都不会丢：vault 就是 git 里的纯 Markdown。自动化部分（命令、角色和提醒）可以安装到 Claude Code 和 Codex 中，两者还能在同一个项目上并行工作。其他任何智能体都能通过 CLI 或 MCP 服务器读到同样的事实。
