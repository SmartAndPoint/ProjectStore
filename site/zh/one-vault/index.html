安装工作原理为何有效一个 vault，多人协作

.projectstore / 方法 / 3

多个会话。多个人。一个 vault。

上下文属于团队，而不属于某个开发者的聊天。ADR 和 spec 像代码一样走合并请求。被评审的是推理过程。

四种工作方式

四种工作方式

多个会话，同一个 vault

两个智能体或两个人同时在同一个 vault 中工作，是常态。每个会话都知道其他会话的存在，几条简单的规则让它们互不干扰。

  • 不会悄悄覆盖。保存新文件之前，ProjectStore 会检查它是否已经存在。两个会话写同一主题时，会得到一次冲突提示，而不是两份副本。
  • 每个状态栏只显示自己的工作。2–6 个会话并排运行，各自只看到属于自己的 epic 和 story。
  • 会话名称只是建议，不是强加。一旦会话的工作集中到某一项上，它就会建议一个名称。频率很低：每个会话最多两次，有记录的九个会话中共建议 12 次。

每个人看到的都不只是自己那一部分。

开发者、技术负责人和 QA 基于同一套决策和标准工作。没有智能体的人只需要 GitHub 或一个 Markdown 编辑器，因为这些都只是普通文件。

整个团队都能用到这份上下文，而不只是发起聊天的那个人。

契约共享，工作分区。

在同一个项目里，API、Web 和平台团队基于共享的 ADR 和 spec，各自推进自己的 epic。共享契约的变更，会在评审中与使用它的团队一起讨论。ProjectStore 会显示哪些 story 依赖它。

谁负责哪些工件、谁来审批契约，由团队自己决定。

执行者不同，依据相同。

规划者读决策和代码地图。实现者读 story 和 spec。评审者读 diff 和标准。每一方拿到的是自己需要的上下文，而不是别人会话的全部历史。在同一个 vault 上工作的会话会互相提醒。

启动智能体并在它们之间交接工作，是你的 harness（智能体运行框架）或编排器的职责。

配置

团队配置，分步说明

  1. 01

    独立的 vault 仓库

    每个项目一个项目文档仓库，而不是每人一个。它与代码仓库并列存放。

  2. 02

    各自检出，共用一个 vault

    每个人克隆 vault 仓库，然后在自己的代码副本中运行 npx projectstore setup 并把那份克隆指定为 vault。绑定信息只保留在本机，不会提交。

  3. 03

    分支加合并请求

    每项决策在被接受之前，都要经过人工评审。critic 在合并请求之前审视它，你的团队在合并请求中评审它。

  4. 04

    在 CI 中运行 doctor

    npx projectstore doctor --json 在 CI 中运行，不需要智能体，也不消耗 token。发现问题时，它会让这一步失败。reconcile --write 也可以在 CI 中重建看板。

Claude Code 和 Codex 可以并排处理同一个项目：它们共用绑定，各自保留自己的智能体模型和会话状态。
