Методика + плагин для Claude Code и Codex

Методика работы для ИИ-агентов, чтобы получать то, что задумали.

ProjectStore — методика и фреймворк для создания приложений и сервисов любой сложности с помощью ИИ-агентов.

В первую очередь это способ работы человека и агентов. Вы решаете, что строить. Агент пишет план, второй агент ищет в нём дыры, вы одобряете. Потом агент делает, а третий сверяет результат с вашим чек-листом — по каждому пункту.

Ставится плагином в Claude Code и Codex. Дальше вы просто говорите с агентом своими словами, а решения, планы и прогресс он сам сохраняет обычными файлами в вашем проекте. Завтра, на другой машине или в другом агенте работа продолжается с того же места.

Установить Как это работает

Работает в Claude Code и Codex. Скоро OpenCode, следом Gemini, Z.ai и DeepSeek.

Почему это работает
  • Ревьюер не закроет задачу, пока не проверен каждый пункт чек-листа.
  • Сессия начинает с доски задач и текущей задачи.
  • Решение записано вместе с причиной, и агент ему следует.
  • Codex читает те же файлы и продолжает.
  • У каждого решения есть файл с причиной и отвергнутыми вариантами.

Установка и начало работы

Начать можно, даже если вы не программист.

Команды за вас выполнит агент. Вам нужно поставить две программы, открыть папку проекта и вставить одну фразу.

Быстрый старт

  1. Поставьте агента

    Агент — программа, которая пишет и запускает код по вашим словам. Подойдёт Claude (приложение, вкладка Code) или Codex от OpenAI.

  2. Поставьте Node.js и откройте папку проекта

    Node.js — среда, в которой работает ProjectStore: установщик LTS с nodejs.org, версия 20 или новее, macOS или Linux. Создайте пустую папку, например «my-bot», и откройте её в агенте.

  3. Установите ProjectStore

    Попросите агента или выполните команду в терминале в папке проекта.

    Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.
    ~/your-project $
    npx projectstore setup

    После установки перезапустите агента; Codex один раз попросит одобрить его хуки.

  4. Скажите, что хотите сделать

    I want to create a stock trading bot

    «Хочу сделать бота для торговли акциями»

  5. Ответьте на вопросы

    Прежде чем планировать, агент спрашивает то, что решать только вам:

    The project is empty—no code, and the vault just has README scaffolding with no epics, stories, or ADRs yet. Per CLAUDE.md, I'll start with an epic and its stories in the vault rather than code, but first I need you to make a few decisions that will shape the plan.

    Перевод: «Проект пустой, кода и заметок пока нет. Начну с плана, а не с кода. Но сначала нужны ваши решения».

    Should the bot trade real money? (торговать реальными деньгами?)

    1. Paper only (Recommended) · учебный счёт
    2. Backtest only · исторические данные, без брокера
    3. Live, with safeguards · аварийная остановка, лимиты позиций и убытка

    Из настоящей сессии Claude Code в пустом проекте, 21 октября 2026. Текст агента дословный, описания вариантов сокращены, русский — перевод.

  6. Одобрите план

    К этому моменту критик его уже проверил. После вашего «да» агент делает работу, а ревьюер сверяет результат с чек-листом.

Как это работает

Цикл с независимой проверкой внутри.

Агенты быстро пишут код и так же быстро пересматривают решённое: каждая новая сессия начинает с нуля. Лечится это не более умным агентом. Лечится циклом «собрать контекст → действовать → проверить», который идёт над проектом, а не только над кодом.

Агенты

6 агентов. Всем, кроме одного, разрешено только читать.

Советники проверяют, планируют и наводят порядок, но ничего не меняют. Один клерк сохраняет только то, что вы одобрили, и только после вашего «да».

criticтолько чтение · независимый

Когда написан или изменён ADR, спека, эпик, стори или дизайн

Ищет слабые места, сверяет каждое утверждение с источником и спрашивает, как план может провалиться. Без лести.

opus · max

До начала работы над стори (story plan)

Смотрит, где в коде живут прошлые эпики. Говорит, где место изменению, что переиспользовать, чего опасаться и в каком порядке работать.

opus · max

После кода, до коммита или story close

Просит подтверждение по каждому критерию приёмки, включая критерии спеки. Затем проверяет корректность, регрессии и тесты.

Находит решения, которые никто не записал: в коде, конфигах и истории git. Предлагает оформить их в ADR, с доказательствами.

Защитные механизмы

Всё держится на механизмах, а не на дисциплине.

Нет стори — напоминание

Агенту, который начал править код без открытой стори, напоминают открыть её. Изменение размером с фичу начинается в vault.

Пометка «без ревью» остаётся

Артефакт, которому нужно ревью, остаётся с review_status: pending, пока не применены итоги проверки критиком. «Ещё без ревью» — это состояние, которое читают инструменты, а не то, что кто-то должен помнить.

Doctor без ИИ

doctor детерминированно проверяет механическую согласованность vault. В CI он работает без агента и без токенов.

Куда смотреть — генерируется

graph.md хранит связи каждого артефакта в обе стороны; code-map.md говорит, где живёт код каждого эпика. Перед архитектурным выбором агента сначала отправляют к индексу ADR.

После /compact vault возвращается

В Claude Code после /compact, запущенного вами, сессия снова начинается со сводки по vault и с файлов vault, которые разговор затрагивал до сжатия.

Вторую сессию предупреждают

Сессия, которая стартует, пока другая работает с тем же vault, открывается с предупреждением о нескольких сессиях: сначала поищите, потом создавайте новое.

«Готово» значит «доказано»

Стори закрывается с подтверждением под каждым критерием.

Ещё до кода планировщик сказал, где место изменению, и план попал в стори после вашего «да»; после кода ревьюер сверил диф с каждым критерием. Каждая строка подтверждения — это тест, выполненная команда или строка кода.

Эти записи может прочитать любой агент, с плагином или без: через CLI, который отвечает JSON и не тратит токены, или через 8 инструментов MCP-сервера, доступных только для чтения.

Оговорки

Оговорки

  • Цикл стоит токенов: черновики, критик и ревьюер работают на модели, за которую вы и так платите. Замеры — в README.
  • Критик и ревьюер в Claude Code — отдельные агенты с чистым контекстом. В Codex эти роли — скиллы.
  • ProjectStore — это общий контекст проекта и способ работы. Это не оркестратор агентов: запуск агентов — задача вашего harness.
Команда и много сессий

Много сессий. Много людей. Один vault.

Контекст принадлежит команде. Не чату одного разработчика. ADR и спеки проходят через pull request, как код. На ревью — ход рассуждений.

Четыре способа работы

Четыре способа работы

Несколько сессий, один vault

Два агента или два человека в одном vault одновременно — это нормально. Каждая сессия знает о других, а несколько простых правил не дают им мешать друг другу.

  • Никаких тихих перезаписей. Перед сохранением нового файла ProjectStore проверяет, что его ещё нет. Две сессии на одну тему получат конфликт, а не две копии.
  • Каждая строка статуса показывает свою работу. 2–6 сессий рядом — и каждая видит ровно свой эпик и свою стори.
  • Имя сессии предлагается, а не навязывается. Когда сессия сосредоточилась на одной задаче, она предлагает для неё имя. Редко: не больше двух раз за сессию, 12 предложений на девять записанных сессий.

Каждый видит не только свою часть.

Разработчик, техлид и QA работают с одними и теми же решениями и критериями. Человеку без агента достаточно GitHub или редактора Markdown: это всего лишь файлы.

Контекст доступен всей команде, а не только владельцу чата.

Общие контракты. Свои зоны работы.

В одном проекте API-, Web- и Platform-команды ведут свои эпики на основе общих ADR и спек. Изменение общего контракта обсуждают на ревью с командами, которые им пользуются. ProjectStore показывает, какие стори от него зависят.

Ответственных за артефакты и согласование контрактов определяет команда.

Разные исполнители. Общие основания.

Планировщик читает решения и карту кода. Исполнитель — стори и спеку. Ревьюер — диф и критерии. Каждый получает нужный ему контекст, а не всю историю чужой сессии. Сессии в одном vault предупреждают друг друга.

Запуск агентов и передача работы между ними — задача вашего harness или оркестратора.

Почему это работает

Индустрия придумала это давно.
Агенты сделали это дешёвым.

ADR, ревью, бэклог, критерии приёмки, связь от цели до кода. Зрелые инженерные команды работают так уже двадцать лет. ProjectStore здесь ничего не изобретает.

Откуда взялась каждая часть

Откуда взялась каждая часть

  1. 1969RFC: решения записаны, пронумерованы и обсуждаются открыто.
  2. 1992DO-178B: в авионике каждое требование должно прослеживаться до кода и до теста.
  3. 1995Scrum: работа как упорядоченный и видимый бэклог.
  4. 1999XP: пользовательские истории и критерии приёмки, по которым видно, что история готова.
  5. 2007Kanban для разработки: доска, которая показывает, что в работе.
  6. 2011ADR, Майкл Найгард: один короткий файл на каждое архитектурное решение.
  7. сейчасАгенты для кода: каждый шаг занимает минуты. Без артефактов каждая сессия начинается с нуля.
Дорогая часть

Процесс всегда был ценным. Дорого было другое: каждый его шаг делали люди.

процесс людей+скорость агентов=ProjectStore

ProjectStore соединяет одно с другим. Скорость агентов впервые делает старый процесс дешёвым. А его документы, которые лежат в файлах рядом с кодом, дают агентам то, чего у них не было: контекст проекта со связями вверх, к целям, и вниз, к коду. По правилу ревью каждого шага проводит второй агент, который не писал черновик. У скорости появляется память, а у памяти — проверка.

Связи хранятся в шапке каждого файла, а подтверждение — это строка под каждым критерием приёмки. Агент заполняет всё это по ходу работы. Карта связей показывает, с чем связан каждый документ. Карта кода — где живёт код каждого эпика. Новая сессия, новая модель или новый коллега начинают с этой цепочки, а не с нуля.
