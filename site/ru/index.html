Агент пишет код. ProjectStore ведёт записи.

Что решено, что в работе, что проверено — в виде Markdown в git, прошедшего ревью. Его читает любой агент и любой, у кого есть доступ к репозиторию.

01 / Установка

Просто попросите агента: Claude Code · Codex · Gemini CLI · Cursor

Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.

В Claude Code этот промпт добавляет git-маркетплейс и ставит плагин из него; включите его автообновление в /plugin. В Codex запустите команду ниже: внутри сессии установка ждёт терминала. Для других агентов плагина пока нет; они читают тот же vault через файлы, CLI и MCP.

Или запустите в терминале: в вашем проекте, вне агента

~/your-project $
npx projectstore setup
▍
Claude CodeCodexGemini CLICursor
  • Спросит, где лежит vault, покажет один план и спросит один раз.
  • Потом перезапустите агента; Codex один раз попросит одобрить хуки.
  • Node.js 20+ · npm для Codex · macOS или Linux
02 / Дальше просто говорите

Команды учить не нужно. Просто спросите.

Скажите, что хотите. Агент запустит нужный процесс, покажет каждый черновик и спросит, прежде чем записать. Сцены ниже — из Claude Code.

1Решение

Решили один раз. «Почему» остаётся.

Решение становится ADR с отклонёнными вариантами. Без вашего «да» ничего не записывается, а потом его проверяет критик с чистым контекстом.

2План

План приходит с критериями приёмки.

Пробелы находятся, пока это ещё фразы, а не баги.

3Разработка

«Готово» значит «доказано».

Планировщик говорит, где место изменению. Ревьюер просит подтверждение по каждому критерию приёмки, прежде чем стори закроется.

4Следующая сессия

Завтра начинается с доски.

Новая сессия открывается со списком того, что в работе. Назовите стори, и агент прочитает её план и чеклист из файла.

Настройки — тоже одной фразой.

барClaude Code · экспериментально

«Покажи проект над строкой ввода».

Текущий эпик, его прогресс и цель, ваша стори и агент, который сейчас работает, — над строкой ввода, прямо во время работы. Пока бар на экране, строка статуса уступает ему место.

моделиClaude Code · Codex: только модели

«Запусти critic на Fable и покажи ProjectStore в строке статуса».

агент запускает:

npx projectstore configure --set agents.critic=fable --set statusline=on
свой скиллClaude Code · Codex: файлы и CLI

«Напиши скилл: перед релизом показывать стори, которые не готовы, и ADR, которые ещё ждут ревью».

Обычный скилл, который читает записи проекта: простой Markdown с frontmatter или 8 MCP-инструментов только для чтения.

Все настройки — из терминала:
npx projectstore configure

Как обновить и как удалить — в README, разделы Upgrading и Uninstalling. При удалении vault остаётся.

04 / Где его место

Не память агента. Не конвейер спек.
Проектные артефакты.

Рядом с агентом, который пишет код, работают инструменты трёх видов. Каждый отвечает на свой вопрос.

ВидВопрос, на который отвечаетПримеры
Память агентаЧто помнит этот агент?Mem0, Zep, память Codex и Claude Code
Файлы инструкцийКак здесь должен вести себя агент?CLAUDE.md, AGENTS.md, правила, steering-файлы
Разработка по спекамКак нам сделать это изменение?Spec Kit, Kiro, OpenSpec, BMAD
ProjectStoreЧто проект решил, что сейчас в работе и проверено ли это?Проектные артефакты — ADR, спеки, эпики, стори, доска — со статусом, датой и связями, в git. Человек одобряет каждый, прежде чем ProjectStore его запишет; критик с чистым контекстом проверяет его по правилу.

Журналы решений, валидаторы, сводка в начале сессии и независимое ревью по отдельности есть и в других инструментах. Вклад ProjectStore — всё это вместе, поверх единого связанного набора записей.

06 / Один или в команде

Один vault. Много сессий, людей и агентов.

Несколько сессий, один vault

Два агента или два человека в одном vault одновременно — это нормально. Каждая сессия знает о других, а несколько простых правил не дают им мешать друг другу.

Каждый видит не только свою часть.

Разработчик, техлид и QA работают с одними и теми же решениями и критериями. Человеку без агента достаточно GitHub или редактора Markdown: это всего лишь файлы.

Общие контракты. Свои зоны работы.

В одном проекте API-, Web- и Platform-команды ведут свои эпики на основе общих ADR и спек. Изменение общего контракта обсуждают на ревью с командами, которые им пользуются. ProjectStore показывает, какие стори от него зависят.

Разные исполнители. Общие основания.

Планировщик читает решения и карту кода. Исполнитель — стори и спеку. Ревьюер — диф и критерии. Каждый получает нужный ему контекст, а не всю историю чужой сессии. Сессии в одном vault предупреждают друг друга.

07 / Метод, доказательства и вопросы

Индустрия придумала это давно.
Агенты сделали это дешёвым.

ADR, ревью, бэклог, критерии приёмки, связь от цели до кода. Зрелые инженерные команды работают так уже двадцать лет. ProjectStore здесь ничего не изобретает.

  1. 1969RFC: решения записаны, пронумерованы и обсуждаются открыто.
  2. 1992DO-178B: в авионике каждое требование должно прослеживаться до кода и до теста.
  3. 1995Scrum: работа как упорядоченный и видимый бэклог.
  4. 1999XP: пользовательские истории и критерии приёмки, по которым видно, что история готова.
  5. 2007Kanban для разработки: доска, которая показывает, что в работе.
  6. 2011ADR, Майкл Найгард: один короткий файл на каждое архитектурное решение.
  7. сейчасАгенты для кода: каждый шаг занимает минуты. Без артефактов каждая сессия начинается с нуля.

Это плагин памяти?

Нет. Плагин памяти помнит, что сказал агент. ProjectStore записывает, что решил проект. Это документы со статусом и датой, прошедшие ревью. Дальше новая работа идёт через эти документы. Разница видна, когда меняется агент, машина или коллега: память принадлежит агенту, пользователю или машине, и даже память, которая хранится в git, — это собственные заметки агента. А vault — это записи проекта: одобренные, прошедшие ревью, со статусом. И он передаётся через git.

Нужен ли Obsidian?

Нет. Vault — обычная папка с файлами Markdown. Открывайте её в редакторе, смотрите на GitHub или используйте Obsidian, если вам нравятся его граф и доска. Без плагина файлы читаются так же хорошо.

Он когда-нибудь пишет без спроса?

Нет. Каждый новый файл или правку вам сначала показывают: путь и весь текст. Затем ждут ответа: «Да», «Править перед сохранением» или «Нет». Помощники, которые следят за разговором, только предлагают команду. Писать может только один агент — клерк. Он запускается после вашего «да» и сохраняет ровно то, что вы одобрили.

Что останется, если его удалить?

Ваш vault остаётся нетронутым: это обычный Markdown в собственном git-репозитории. Привязка проекта и модели агентов команды тоже остаются, поэтому повторная установка их найдёт. Плагин Codex зарегистрирован для всех проектов на машине, поэтому его удаление — отдельный шаг. Как удалить
