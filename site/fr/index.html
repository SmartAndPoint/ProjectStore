Votre agent écrit le code. ProjectStore garde le registre.

Ce qui a été décidé, ce qui est en cours, ce qui a été vérifié — en Markdown relu, dans git, lisible par n'importe quel agent et par quiconque a accès au dépôt.

01 / Installation

Demandez simplement à votre agent : Claude Code · Codex · Gemini CLI · Cursor

Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.

Dans Claude Code, ce prompt ajoute la marketplace git et installe le plugin depuis celle-ci ; activez sa mise à jour automatique dans /plugin. Dans Codex, lancez plutôt la commande ci-dessous : dans une session, l'installation attend un terminal. Les autres agents n'ont pas encore de plugin ; ils lisent le même vault via ses fichiers, la CLI et MCP.

Ou lancez-la dans un terminal : dans votre projet, hors de l'agent

~/your-project $
npx projectstore setup

02 / Ensuite, il suffit de parler

Aucune commande à apprendre. Il suffit de parler.

Dites ce que vous voulez. L'agent déroule le workflow, montre chaque brouillon et demande avant d'écrire. Les scènes ci-dessous sont celles de Claude Code.

1Décider

Décidez une fois. Le pourquoi reste.

Une décision devient un ADR avec ses alternatives écartées. Rien n'est écrit sans votre oui, et un critic au contexte neuf le relit ensuite.

2Planifier

Les plans viennent avec leurs critères d'acceptation.

Les lacunes se repèrent quand ce ne sont encore que des phrases, pas des bugs.

3Réaliser

Terminé veut dire prouvé.

Le planner dit où le changement a sa place. Le reviewer demande une preuve pour chaque critère d'acceptation avant la clôture de la story.

4La session suivante

Demain repart du tableau.

Une nouvelle session s'ouvre sur ce qui est en cours. Nommez une story, et l'agent lit son plan et sa checklist dans le fichier.

Les réglages aussi tiennent en une phrase.

le bandeauClaude Code · expérimental

« Affiche le projet au-dessus de mon prompt. »

L'epic où vous êtes, son avancement, son objectif, votre story et l'agent au travail — au-dessus du prompt, pendant que vous travaillez. Quand il s'affiche, la ligne de statut s'efface.

06 / Seul ou en équipe

Un vault. Plusieurs sessions, personnes et agents.

Plusieurs sessions, un seul vault

Deux agents ou deux personnes dans le même vault au même moment : c'est normal. Chaque session sait que les autres existent, et quelques règles simples les empêchent de se marcher dessus.

Chacun voit plus que sa propre partie.

Le développeur, le tech lead et la QA travaillent à partir des mêmes décisions et des mêmes critères. Une personne sans agent n'a besoin que de GitHub ou d'un éditeur Markdown : ce ne sont que des fichiers.

Des contrats partagés. Des périmètres de travail distincts.

Dans un même projet, les équipes API, Web et Plateforme mènent leurs propres epics en s'appuyant sur des ADR et des specs partagés. Un changement de contrat partagé se discute en revue avec les équipes qui l'utilisent. ProjectStore montre quelles stories en dépendent.

Des exécutants différents. Des bases communes.

Le planner lit les décisions et la carte du code. L'implémenteur lit la story et la spec. Le reviewer lit le diff et les critères. Chacun reçoit le contexte dont il a besoin, pas tout l'historique de la session de quelqu'un d'autre. Les sessions sur un même vault se préviennent mutuellement.

07 / La méthode, les preuves et les questions

L'industrie a inventé cela il y a longtemps.
Les agents l'ont rendu bon marché.

Des ADR, des revues, un backlog, des critères d'acceptation, des liens de l'objectif jusqu'au code. Les équipes d'ingénierie matures travaillent ainsi depuis vingt ans. ProjectStore n'en invente rien.

  1. 1969RFC : des décisions écrites et numérotées, puis discutées au grand jour.
  2. 1992DO-178B : en avionique, chaque exigence doit être reliée au code et à un test.
  3. 1995Scrum : le travail sous forme de backlog, ordonné et visible.
  4. 1999XP : les user stories, et des critères d'acceptation qui disent quand une story est terminée.
  5. 2007Kanban pour le logiciel : un tableau qui montre ce qui est en cours.
  6. 2011ADR, Michael Nygard : un court fichier par décision d'architecture.
  7. présentLes agents de codage : chaque étape prend quelques minutes. Sans les artefacts, chaque session repart de zéro.

Les deux chiffres : README — What it costs

Est-ce un plugin de mémoire ?

Non. Un plugin de mémoire retient ce que l'agent a dit. ProjectStore consigne ce que le projet a décidé, sous forme de documents relus, avec un statut et une date. Le nouveau travail passe ensuite par ces documents. La différence se voit quand vous changez d'agent, de machine ou de coéquipier : la mémoire appartient à un agent, à un utilisateur ou à une machine, et même conservée dans git, une mémoire reste un ensemble de notes propres à l'agent ; le vault est le registre du projet — validé, relu, avec un statut — et il circule par git.

Obsidian est-il nécessaire ?

Non. Le vault est un dossier ordinaire de fichiers Markdown. Ouvrez-le dans un éditeur, parcourez-le sur GitHub, ou utilisez Obsidian si vous aimez son graphe et son tableau. Sans le plugin, les fichiers restent tout aussi lisibles.

Lui arrive-t-il d'écrire sans demander ?

Non. Chaque nouveau fichier et chaque modification vous sont d'abord montrés, avec leur chemin et leur texte complet. Puis ProjectStore attend Oui, Modifier avant d'enregistrer, ou Non. Les assistants qui observent la conversation ne font que suggérer une commande. Le seul agent capable d'écrire, le clerk, intervient après votre Oui et enregistre exactement ce que vous avez validé.

Que reste-t-il si je le désinstalle ?

Votre vault, intact : c'est du Markdown dans son propre dépôt git. La liaison du projet et les modèles d'agents de l'équipe restent aussi, si bien qu'une nouvelle installation les retrouve.
