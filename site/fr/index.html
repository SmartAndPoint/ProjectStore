Une méthode et un plugin pour Claude Code et Codex

Une méthode pour travailler avec des agents IA qui fonctionne vraiment.

ProjectStore est une méthode et un framework pour construire des applications et des services de toute taille avec des agents IA.

C'est d'abord une manière de travailler ensemble, pour une personne et des agents. Vous décidez ce qu'il faut construire. Un agent écrit le plan, un deuxième agent y cherche les failles, et vous validez. Ensuite l'agent construit, et un troisième vérifie le résultat à partir de votre liste de contrôle, point par point.

Il s'installe comme plugin dans Claude Code et Codex. Dès lors, vous parlez à l'agent avec vos propres mots, et il garde les décisions, les plans et l'avancement sous forme de simples fichiers dans votre projet. Demain, sur une autre machine ou dans un autre agent, le travail reprend là où il s'était arrêté.

Installer Comment ça marche

Fonctionne dans Claude Code et Codex. OpenCode bientôt ; Gemini, Z.ai et DeepSeek ensuite.

Pourquoi ça marche
  • Le reviewer ne clôt pas la tâche tant que chaque point de la liste de contrôle n'est pas coché.
  • La session démarre à partir du tableau des tâches et de la story en cours.
  • La décision est écrite avec sa raison, et l'agent la suit.
  • Codex lit les mêmes fichiers et poursuit le travail.
  • Chaque décision a un fichier avec la raison et les options que vous avez écartées.

Installation et premiers pas

Vous pouvez commencer même si vous n'êtes pas programmeur.

Votre agent lance les commandes pour vous. Vous installez deux programmes, vous ouvrez un dossier de projet et vous collez une phrase.

Démarrage rapide

  1. Prendre un agent

    Un agent est un programme qui écrit et exécute du code à partir de vos mots. L'un ou l'autre convient : Claude (l'application, son onglet Code) ou Codex d'OpenAI.

  2. Installer Node.js et ouvrir un dossier de projet

    Node.js est ce sur quoi ProjectStore fonctionne : l'installeur LTS de nodejs.org, version 20 ou plus récente, sur macOS ou Linux. Créez un dossier vide, par exemple « my-bot », et ouvrez-le dans l'agent.

  3. Installer ProjectStore

    Demandez à votre agent ou lancez la commande dans un terminal, dans le dossier du projet.

    Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.
    ~/your-project $
    npx projectstore setup

    Après l'installation, redémarrez l'agent ; Codex demande une seule fois d'approuver ses hooks.

  4. Dire ce que vous voulez construire

    I want to create a stock trading bot

    « Je veux créer un bot pour trader des actions »

  5. Répondre à ses questions

    L'agent demande ce que vous seul pouvez décider, avant de planifier :

    The project is empty—no code, and the vault just has README scaffolding with no epics, stories, or ADRs yet. Per CLAUDE.md, I'll start with an epic and its stories in the vault rather than code, but first I need you to make a few decisions that will shape the plan.

    Traduction : « Le projet est vide, il n'y a pas encore de code ni de notes. Je commencerai par un plan, pas par du code. Mais j'ai d'abord besoin de vos décisions. »

    Should the bot trade real money? (trader avec de l'argent réel ?)

    1. Paper only (Recommended) · compte d'essai (paper trading)
    2. Backtest only · données historiques, pas de courtier
    3. Live, with safeguards · coupe-circuit, limites de position, plafond de perte quotidienne

    D'une vraie session Claude Code sur un projet vide, le 21 octobre 2026. Le texte de l'agent est cité mot pour mot ; les détails des options sont raccourcis.

  6. Approuver le plan

    Le critic l'a déjà vérifié. Après votre oui, l'agent le construit, et le reviewer vérifie le résultat à partir de la liste de contrôle.

Comment ça marche

Une boucle qui intègre une vérification indépendante.

Les agents écrivent vite du code, et rouvrent tout aussi vite des questions déjà tranchées : chaque nouvelle session arrive vide. La solution n'est pas un agent plus malin. C'est rassembler le contexte → agir → vérifier, appliqué au projet et pas seulement au code.

Les agents

6 agents. Chacun ne règle que sa propre tâche.

Les conseillers vérifient, planifient et rangent, sans rien modifier. Un seul clerk enregistre, après votre Oui, ce que vous avez validé et rien d'autre.

criticlecture seule · indépendant

Après l'écriture ou la modification d'un ADR, d'une spec, d'un epic, d'une story ou d'un document de conception

Cherche les points faibles, confronte chaque affirmation à la source et se demande comment le plan pourrait échouer. Sans complaisance.

Les garde-fous

Ce sont des mécanismes qui tiennent l'ensemble, pas la discipline.

Pas de story, un rappel

Un agent qui se met à modifier du code sans story ouverte reçoit un rappel pour en ouvrir une. Un changement de la taille d'une fonctionnalité commence dans le vault.

Ce qui n'est pas relu reste marqué

Un artefact qui demande une relecture porte review_status: pending jusqu'à ce qu'un passage du critic soit appliqué. « Pas encore relu » est un état que les outils savent lire, pas quelque chose dont quelqu'un doit se souvenir.

Un doctor sans IA

doctor vérifie de façon déterministe la cohérence mécanique du vault. En CI, il tourne sans agent et sans tokens.

Où regarder, généré

graph.md contient les liens de chaque artefact dans les deux sens ; code-map.md indique où vit le code de chaque epic. Avant un choix d'architecture, l'agent est d'abord dirigé vers l'index des ADR.

Après /compact, le vault revient

Dans Claude Code, après un /compact que vous lancez, la session repart avec l'orientation du vault, et avec les fichiers du vault que la conversation avait touchés auparavant.

Une deuxième session est prévenue

Une session qui démarre pendant qu'une autre travaille sur le même vault s'ouvre avec un avertissement multi-session : cherchez avant de créer quoi que ce soit de nouveau.

Terminé veut dire prouvé

Une story se clôt avec une preuve sous chaque critère.

Le planner a dit où le changement a sa place avant le code, et le plan a été ajouté à la story après votre oui ; le reviewer a ensuite vérifié le diff critère par critère. Chaque ligne de preuve est un test, une commande exécutée ou une ligne de code.

En petits caractères

En petits caractères

  • Faire tourner la boucle coûte des tokens : les brouillons, le critic et le reviewer s'exécutent sur le modèle que vous payez déjà. Le README chiffre ce coût.
  • Dans Claude Code, le critic et le reviewer sont des agents distincts, au contexte neuf. Dans Codex, les rôles sont des skills.
  • ProjectStore est un contexte de projet partagé et une manière de travailler. Ce n'est pas un orchestrateur d'agents : lancer les agents est le rôle de votre harness.
Équipe et plusieurs sessions

Plusieurs sessions. Plusieurs personnes. Un seul vault.

Le contexte appartient à l'équipe, pas au chat d'un seul développeur. Les ADR et les specs passent par des pull requests, comme le code. Ce qu'on relit, c'est le raisonnement.

Quatre façons de travailler

Quatre façons de travailler

Plusieurs sessions, un seul vault

Deux agents ou deux personnes dans le même vault au même moment : c'est normal. Chaque session sait que les autres existent, et quelques règles simples les empêchent de se marcher dessus.

  • Pas d'écrasement silencieux. Avant d'enregistrer un nouveau fichier, ProjectStore vérifie qu'il n'existe pas encore. Deux sessions sur le même sujet tombent sur un conflit, pas sur deux copies.
  • Chaque ligne de statut affiche son propre travail. 2–6 sessions côte à côte voient chacune exactement leur epic et leur story.
  • Les noms de session sont proposés, pas imposés. Quand une session se concentre sur un travail précis, elle propose un nom. Rarement : deux fois par session au plus, 12 propositions sur neuf sessions enregistrées.

Chacun voit plus que sa propre partie.

Le développeur, le tech lead et la QA travaillent à partir des mêmes décisions et des mêmes critères. Une personne sans agent n'a besoin que de GitHub ou d'un éditeur Markdown : ce ne sont que des fichiers.

Le contexte est accessible à toute l'équipe, pas seulement au propriétaire du chat.

Des contrats partagés. Des périmètres de travail distincts.

Dans un même projet, les équipes API, Web et Plateforme mènent leurs propres epics en s'appuyant sur des ADR et des specs partagés. Un changement de contrat partagé se discute en revue avec les équipes qui l'utilisent. ProjectStore montre quelles stories en dépendent.

Qui possède quels artefacts et qui valide les contrats, c'est à l'équipe d'en décider.

Des exécutants différents. Des bases communes.

Le planner lit les décisions et la carte du code. L'implémenteur lit la story et la spec. Le reviewer lit le diff et les critères. Chacun reçoit le contexte dont il a besoin, pas tout l'historique de la session de quelqu'un d'autre. Les sessions sur un même vault se préviennent mutuellement.

Lancer les agents et faire passer le travail de l'un à l'autre, c'est le rôle de votre harness ou de votre orchestrateur.

Pourquoi ça marche

L'industrie a inventé cela il y a longtemps.
Les agents l'ont rendu bon marché.

Des ADR, des revues, un backlog, des critères d'acceptation, des liens de l'objectif jusqu'au code. Les équipes d'ingénierie matures travaillent ainsi depuis vingt ans. ProjectStore n'en invente rien.

D'où vient chaque élément

D'où vient chaque élément

  1. 1969RFC : des décisions écrites et numérotées, puis discutées au grand jour.
  2. 1992DO-178B : en avionique, chaque exigence doit être reliée au code et à un test.
  3. 1995Scrum : le travail sous forme de backlog, ordonné et visible.
  4. 1999XP : les user stories, et des critères d'acceptation qui disent quand une story est terminée.
  5. 2007Kanban pour le logiciel : un tableau qui montre ce qui est en cours.
  6. 2011ADR, Michael Nygard : un court fichier par décision d'architecture.
  7. présentLes agents de codage : chaque étape prend quelques minutes. Sans les artefacts, chaque session repart de zéro.
Ce qui coûtait cher

Le processus a toujours eu de la valeur. Ce qui coûtait cher, c'était que des humains en assurent chaque étape.

le processus des humains+la vitesse des agents=ProjectStore

ProjectStore réunit les deux. La vitesse des agents rend le vieux processus bon marché pour la première fois. Ses documents, rangés dans des fichiers à côté du code, donnent aux agents ce qu'ils n'ont jamais eu : le contexte du projet, relié en amont aux objectifs et en aval au code. La règle veut qu'un second agent, qui n'a pas écrit le brouillon, relise chaque étape. La vitesse y gagne une mémoire, et la mémoire une vérification.

Une nouvelle session, un nouveau modèle ou un nouveau collègue part de cette chaîne, pas de zéro.
