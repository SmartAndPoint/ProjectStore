Eine Methode und ein Plugin für Claude Code und Codex

Eine Methode für die Arbeit mit KI-Agenten, damit du bekommst, was du dir vorgestellt hast.

ProjectStore ist eine Methode und ein Framework, um Apps und Dienste jeder Größe mit KI-Agenten zu bauen.

Zuallererst ist es eine Art, wie Mensch und Agenten zusammenarbeiten. Du entscheidest, was gebaut wird. Ein Agent schreibt den Plan, ein zweiter Agent sucht darin nach Lücken, und du gibst frei. Dann baut der Agent, und ein dritter prüft das Ergebnis Punkt für Punkt gegen deine Checkliste.

Es wird als Plugin in Claude Code und Codex installiert. Ab dann sprichst du mit dem Agenten in deinen eigenen Worten, und er hält Entscheidungen, Pläne und Fortschritt als einfache Dateien in deinem Projekt fest. Morgen, auf einem anderen Rechner oder in einem anderen Agenten, geht die Arbeit dort weiter, wo sie aufgehört hat.

Installieren So funktioniert es

Funktioniert in Claude Code und Codex. OpenCode bald; Gemini, Z.ai und DeepSeek als Nächstes.

Warum es funktioniert
  • Der Reviewer schließt die Aufgabe erst, wenn jeder Punkt der Checkliste abgehakt ist.
  • Die Sitzung beginnt mit dem Aufgabenboard und der Story, die in Arbeit ist.
  • Die Entscheidung wird mit ihrer Begründung aufgeschrieben, und der Agent hält sich daran.
  • Codex liest dieselben Dateien und macht weiter.
  • Zu jeder Entscheidung gibt es eine Datei mit der Begründung und den Optionen, die du abgelehnt hast.

ProjectStore nimmt von allen das Beste: deine eigenen Worte, Gedächtnis zwischen Sitzungen, eine Spec vor dem Code und Nachweis danach. Und es hält das für das ganze Projekt und das ganze Team fest, nicht für ein Feature oder einen Rechner.

Installation und erste Schritte

Du kannst auch starten, wenn du kein Programmierer bist.

Dein Agent führt die Befehle für dich aus. Du installierst zwei Programme, öffnest einen Projektordner und fügst einen Satz ein.

Schnellstart

  1. Einen Agenten besorgen

    Ein Agent ist ein Programm, das aus deinen Worten Code schreibt und ausführt. Beides funktioniert: Claude (die App, ihr Tab Code) oder Codex von OpenAI.

  2. Node.js installieren und einen Projektordner öffnen

    Node.js ist die Grundlage, auf der ProjectStore läuft: der LTS-Installer von nodejs.org, Version 20 oder neuer, unter macOS oder Linux. Lege einen leeren Ordner an, zum Beispiel „my-bot“, und öffne ihn im Agenten.

  3. ProjectStore installieren

    Bitte deinen Agenten darum oder führe den Befehl in einem Terminal im Projektordner aus.

    Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.
    ~/your-project $
    npx projectstore setup

    Starte den Agenten nach der Installation neu; Codex bittet einmal darum, seine Hooks freizugeben.

  4. Sag, was du bauen willst

    I want to create a stock trading bot

    „Ich möchte einen Bot für den Aktienhandel bauen“

  5. Beantworte seine Fragen

    Der Agent fragt, was nur du entscheiden kannst, bevor er plant:

    The project is empty—no code, and the vault just has README scaffolding with no epics, stories, or ADRs yet. Per CLAUDE.md, I'll start with an epic and its stories in the vault rather than code, but first I need you to make a few decisions that will shape the plan.

    Übersetzung: „Das Projekt ist leer, es gibt noch keinen Code und keine Notizen. Ich beginne mit einem Plan, nicht mit Code. Vorher brauche ich aber deine Entscheidungen.“

    Should the bot trade real money? (mit echtem Geld handeln?)

    1. Paper only (Recommended) · Papier-/Sandbox-Konto
    2. Backtest only · historische Daten, kein Broker
    3. Live, with safeguards · Notaus, Positionslimits, Tagesverlustgrenze

    Aus einer echten Sitzung in Claude Code, in einem leeren Projekt, 21. Oktober 2026. Der Text des Agenten ist wörtlich zitiert; die Details der Optionen sind gekürzt.

  6. Den Plan freigeben

    Der Critic hat ihn bis dahin geprüft. Nach deinem Ja baut der Agent ihn, und der Reviewer prüft das Ergebnis gegen die Checkliste.

So funktioniert es

Eine Schleife mit einer unabhängigen Prüfung darin.

Agenten schreiben schnell Code, und sie entscheiden Geklärtes genauso schnell neu: Jede frische Sitzung beginnt leer. Die Lösung ist kein klügerer Agent, sondern Kontext sammeln → handeln → prüfen, angewandt auf das Projekt und nicht nur auf den Code.

Die Agenten

6 Agenten. Alle bis auf einen dürfen nur lesen.

Die Berater prüfen, planen und räumen auf, ohne etwas zu ändern. Ein einziger Clerk speichert nach deinem Ja nur das, was du freigegeben hast.

criticnur lesend · unabhängig

Nachdem ein ADR, eine Spec, ein Epic, eine Story oder ein Design geschrieben oder geändert wurde

Sucht nach Schwachstellen, prüft jede Behauptung an der Quelle und fragt, wie der Plan scheitern könnte. Keine Schmeichelei.

opus · max
plannernur lesend · unabhängig

Bevor die Arbeit an einer Story beginnt (story plan)

Schaut, wo frühere Epics im Code liegen. Sagt, wo die Änderung hingehört, was sich wiederverwenden lässt, worauf zu achten ist und in welcher Reihenfolge gearbeitet wird.

opus · max
reviewernur lesend · unabhängig

Wenn der Code steht, vor dem Commit oder story close

Verlangt einen Nachweis für jedes Abnahmekriterium, auch für die der Spec. Prüft dann Korrektheit, Regressionen und Tests.

opus · max
librariannur lesend · schlägt vor

Ab und zu, vor Releases, wenn der Vault schnell wächst

Findet, was keine Regel erkennt: Research-Notizen, die einem akzeptierten ADR widersprechen, Duplikate, fehlende Links, Dateien, die ins Archiv können.

opus · max
archaeologistnur lesend · schlägt vor

Einmal, nach dem Binden einer bestehenden Codebasis

Findet Entscheidungen, die niemand aufgeschrieben hat: im Code, in Konfigurationsdateien und in der Git-Historie. Schlägt dafür ADRs vor, mit Nachweisen.

opus · max
clerkschreibt · nach deinem Ja

Nur innerhalb eines Befehlsablaufs, nur nach deinem Ja

Speichert genau das, was du freigegeben hast, nicht mehr. Baut danach das Board neu auf und führt die Prüfungen aus. Schreibt nichts Eigenes und fragt nichts.

sonnet · max

Die Standardmodelle gelten für Claude Code. In Codex ist jede Rolle ein gleichnamiger Skill, der Codex bittet, die Rolle zu starten, etwa $projectstore-critic für den Critic; er nutzt das Modell der Sitzung, solange du keines festlegst.

Die Schutzmechanismen

Mechanismen halten es zusammen, nicht Disziplin.

Keine Story, ein Stups

Ein Agent, der Code zu bearbeiten beginnt, ohne dass eine Story offen ist, wird daran erinnert, eine zu öffnen. Eine Änderung in Feature-Größe beginnt im Vault.

Was nicht reviewt ist, bleibt markiert

Ein Artefakt, das ein Review braucht, trägt review_status: pending, bis ein Critic-Durchgang eingearbeitet ist. „Noch nicht reviewt“ ist ein Zustand, den die Werkzeuge lesen können, nichts, woran sich jemand erinnern muss.

Ein Doctor ohne KI

doctor prüft die mechanische Konsistenz des Vaults deterministisch. In der CI läuft er ohne Agent und ohne Tokens.

Wo man nachschaut, generiert

graph.md hält die Links jedes Artefakts in beiden Richtungen fest; code-map.md sagt, wo der Code jedes Epics liegt. Vor einer Architekturentscheidung wird der Agent zuerst auf den ADR-Index verwiesen.

Nach /compact kommt der Vault zurück

Nach einem /compact, das du ausführst, beginnt die Sitzung in Claude Code wieder mit der Orientierung des Vaults und mit den Vault-Dateien, die das Gespräch zuvor berührt hat.

Eine zweite Sitzung wird gewarnt

Eine Sitzung, die startet, während eine andere am selben Vault arbeitet, beginnt mit einer Multi-Session-Warnung: erst suchen, bevor etwas Neues entsteht.

Fertig heißt bewiesen

Eine Story schließt mit Nachweis unter jedem Kriterium.

Der Planner hat vor dem Code gesagt, wo die Änderung hingehört, und der Plan ging mit deinem Ja in die Story; danach hat der Reviewer den Diff gegen jedes Kriterium geprüft. Jede Zeile Nachweis ist ein Test, ein ausgeführter Befehl oder eine Codezeile.

Jeder Agent kann diese Akte lesen, mit oder ohne Plugin: über die CLI, die mit JSON antwortet und keine Tokens braucht, oder über die 8 schreibgeschützten Tools des MCP-Servers.

Kleingedrucktes

Kleingedrucktes

  • Die Schleife zu betreiben kostet Tokens: Die Entwürfe, der Critic und der Reviewer laufen auf dem Modell, das du ohnehin bezahlst. Das README misst es.
  • Critic und Reviewer sind in Claude Code getrennte Agenten mit frischem Kontext. In Codex sind die Rollen Skills.
  • ProjectStore ist geteilter Projektkontext und eine Arbeitsweise. Es ist kein Agenten-Orchestrator: Agenten zu starten ist Aufgabe deines Harness.
Team und viele Sitzungen

Viele Sitzungen. Viele Menschen. Ein Vault.

Der Kontext gehört dem Team, nicht dem Chat eines einzelnen Entwicklers. ADRs und Specs laufen wie Code über Pull Requests. Reviewt wird die Begründung.

Vier Arten zu arbeiten

Vier Arten zu arbeiten

Mehrere Sitzungen, ein Vault

Dass zwei Agenten oder zwei Menschen gleichzeitig in einem Vault arbeiten, ist normal. Jede Sitzung weiß von den anderen, und ein paar einfache Regeln sorgen dafür, dass sie sich nicht in die Quere kommen.

  • Kein stilles Überschreiben. Bevor ProjectStore eine neue Datei speichert, prüft es, ob sie schon existiert. Zwei Sitzungen zum selben Thema bekommen einen Konflikt, keine zwei Kopien.
  • Jede Statuszeile zeigt die eigene Arbeit. 2–6 Sitzungen nebeneinander sehen jeweils genau ihr eigenes Epic und ihre eigene Story.
  • Sitzungsnamen werden angeboten, nicht aufgezwungen. Sobald sich eine Sitzung auf eine Aufgabe festlegt, schlägt sie einen Namen dafür vor. Selten: höchstens zweimal pro Sitzung, 12 Vorschläge in neun aufgezeichneten Sitzungen.

Alle sehen mehr als ihren eigenen Teil.

Entwickler, Tech Lead und QA arbeiten mit denselben Entscheidungen und Kriterien. Wer keinen Agenten nutzt, braucht nur GitHub oder einen Markdown-Editor: Es sind einfach Dateien.

Der Kontext steht dem ganzen Team zur Verfügung, nicht nur dem Besitzer des Chats.

Gemeinsame Verträge. Getrennte Arbeitsbereiche.

In einem Projekt führen die Teams API, Web und Plattform ihre eigenen Epics auf Basis gemeinsamer ADRs und Specs. Eine Änderung an einem gemeinsamen Vertrag wird im Review mit den Teams besprochen, die ihn nutzen. ProjectStore zeigt, welche Stories davon abhängen.

Wem welche Artefakte gehören und wer Verträge abzeichnet, entscheidet das Team.

Verschiedene Ausführende. Gemeinsame Grundlage.

Der Planner liest die Entscheidungen und die Code-Map. Der Implementierer liest Story und Spec. Der Reviewer liest Diff und Kriterien. Jeder bekommt den Kontext, den er braucht, nicht den ganzen Verlauf einer fremden Sitzung. Sitzungen im selben Vault warnen einander.

Agenten zu starten und Arbeit zwischen ihnen zu übergeben, ist Aufgabe deines Harness oder Orchestrators.

Warum es funktioniert

Die Branche hat das längst erfunden.
Agenten haben es günstig gemacht.

ADRs, Reviews, ein Backlog, Abnahmekriterien, Verknüpfungen vom Ziel bis zum Code. Reife Engineering-Teams arbeiten seit zwanzig Jahren so. ProjectStore erfindet nichts davon.

Woher jedes Stück kommt

Woher jedes Stück kommt

  1. 1969RFCs: Entscheidungen, aufgeschrieben und nummeriert, dann offen diskutiert.
  2. 1992DO-178B: In der Avionik muss jede Anforderung auf Code und auf einen Test zurückführbar sein.
  3. 1995Scrum: die Arbeit als Backlog, geordnet und sichtbar.
  4. 1999XP: User Stories und Abnahmekriterien, die sagen, wann eine fertig ist.
  5. 2007Kanban für Software: ein Board, das zeigt, was in Arbeit ist.
  6. 2011ADRs, Michael Nygard: eine kurze Datei pro Architekturentscheidung.
  7. jetztCoding-Agenten: Jeder Schritt dauert Minuten. Ohne die Artefakte beginnt jede Sitzung leer.
Der teure Teil

Der Prozess war immer wertvoll. Teuer war, dass Menschen jeden Schritt selbst ausführten.

Prozess der Menschen+Tempo der Agenten=ProjectStore

ProjectStore bringt beides zusammen. Die Geschwindigkeit von Agenten macht den alten Prozess zum ersten Mal günstig. Die Dokumente dieses Prozesses liegen als Dateien neben dem Code und geben Agenten, was sie nie hatten: den Kontext des Projekts, verknüpft nach oben mit den Zielen und nach unten mit dem Code. Jeden Schritt reviewt laut Arbeitsregel ein zweiter Agent, der den Entwurf nicht geschrieben hat. Geschwindigkeit bekommt ein Gedächtnis, und das Gedächtnis eine Prüfung.

Eine neue Sitzung, ein neues Modell oder ein neuer Kollege startet von dieser Kette aus, nicht bei null.
