Dein Agent schreibt den Code. ProjectStore führt die Akte.

Was entschieden wurde, was in Arbeit ist, was geprüft wurde — als reviewtes Markdown in git, lesbar für jeden Agenten und jeden mit Zugriff auf das Repo.

01 / Installieren

Frag einfach deinen Agenten: Claude Code · Codex · Gemini CLI · Cursor

Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.

In Claude Code fügt dieser Prompt den Git-Marketplace hinzu und installiert daraus; schalte dessen automatisches Update in /plugin ein. In Codex führst du stattdessen den Befehl unten aus: Innerhalb einer Sitzung wartet die Installation auf ein Terminal. Andere Agenten bekommen noch kein Plugin; sie lesen denselben Vault über seine Dateien, die CLI und MCP.

Oder im Terminal ausführen: in deinem Projekt, außerhalb des Agenten

~/your-project $
npx projectstore setup

02 / Dann einfach reden

Keine Befehle zu lernen. Einfach reden.

Sag, was du willst. Der Agent führt den Ablauf aus, zeigt jeden Entwurf und fragt, bevor er schreibt. Die Szenen unten zeigen Claude Code.

1Entscheiden

Einmal entscheiden. Das Warum bleibt.

Aus einer Entscheidung wird ein ADR samt verworfenen Alternativen. Ohne dein Ja wird nichts geschrieben, und danach reviewt es ein Critic mit frischem Kontext.

2Planen

Zu jedem Plan gehören Abnahmekriterien.

Lücken fallen auf, solange sie noch Sätze sind und keine Bugs.

3Bauen

Fertig heißt bewiesen.

Der Planner sagt, wo die Änderung hingehört. Der Reviewer verlangt für jedes Abnahmekriterium einen Nachweis, bevor die Story geschlossen wird.

4Die nächste Sitzung

Morgen beginnt am Board.

Eine neue Sitzung beginnt mit dem, was gerade in Arbeit ist. Nenn eine Story, und der Agent liest Plan und Checkliste aus der Datei.

Einstellungen sind auch nur ein Satz.

die LeisteClaude Code · experimentell

„Zeig das Projekt über meinem Prompt an.“

Das Epic, in dem du bist, wie weit es fortgeschritten ist, sein Ziel, deine Story und der Agent bei der Arbeit — über dem Prompt, während du arbeitest. Solange sie angezeigt wird, macht die Statuszeile Platz.

04 / Wo es sich einordnet

Kein Agenten-Gedächtnis. Keine Spec-Pipeline.
Projektartefakte.

Neben einem Coding-Agenten stehen drei Arten von Werkzeugen. Jede beantwortet eine andere Frage.

ArtDie Frage, die sie beantwortetBeispiele
AgentengedächtnisWoran erinnert sich dieser Agent?Mem0, Zep, das Gedächtnis von Codex und Claude Code
AnweisungsdateienWie soll sich ein Agent hier verhalten?CLAUDE.md, AGENTS.md, Regeln, Steering-Dateien
Spec-getriebene WerkzeugeWie setzen wir diese Änderung um?Spec Kit, Kiro, OpenSpec, BMAD
ProjectStoreWas hat das Projekt entschieden, was ist in Arbeit, und wurde es geprüft?Projektartefakte — ADRs, Specs, Epics, Stories, das Board — mit Status, Datum und Links, in git. Ein Mensch gibt jedes frei, bevor ProjectStore es schreibt; ein Critic mit frischem Kontext reviewt es laut Arbeitsregel.

Entscheidungslogs, Validatoren, eine Orientierung zum Sitzungsstart und unabhängiges Review gibt es jeweils auch anderswo. Was ProjectStore hinzufügt, ist all das zusammen auf einer einzigen verknüpften Akte.

06 / Allein oder im Team

Ein Vault. Viele Sitzungen, Menschen und Agenten.

Mehrere Sitzungen, ein Vault

Dass zwei Agenten oder zwei Menschen gleichzeitig in einem Vault arbeiten, ist normal. Jede Sitzung weiß von den anderen, und ein paar einfache Regeln sorgen dafür, dass sie sich nicht in die Quere kommen.

Alle sehen mehr als ihren eigenen Teil.

Entwickler, Tech Lead und QA arbeiten mit denselben Entscheidungen und Kriterien. Wer keinen Agenten nutzt, braucht nur GitHub oder einen Markdown-Editor: Es sind einfach Dateien.

Gemeinsame Verträge. Getrennte Arbeitsbereiche.

In einem Projekt führen die Teams API, Web und Plattform ihre eigenen Epics auf Basis gemeinsamer ADRs und Specs. Eine Änderung an einem gemeinsamen Vertrag wird im Review mit den Teams besprochen, die ihn nutzen. ProjectStore zeigt, welche Stories davon abhängen.

Verschiedene Ausführende. Gemeinsame Grundlage.

Der Planner liest die Entscheidungen und die Code-Map. Der Implementierer liest Story und Spec. Der Reviewer liest Diff und Kriterien. Jeder bekommt den Kontext, den er braucht, nicht den ganzen Verlauf einer fremden Sitzung. Sitzungen im selben Vault warnen einander.

07 / Die Methode, Belege und Fragen

Die Branche hat das längst erfunden.
Agenten haben es günstig gemacht.

ADRs, Reviews, ein Backlog, Abnahmekriterien, Verknüpfungen vom Ziel bis zum Code. Reife Engineering-Teams arbeiten seit zwanzig Jahren so. ProjectStore erfindet nichts davon.

  1. 1969RFCs: Entscheidungen, aufgeschrieben und nummeriert, dann offen diskutiert.
  2. 1992DO-178B: In der Avionik muss jede Anforderung auf Code und auf einen Test zurückführbar sein.
  3. 1995Scrum: die Arbeit als Backlog, geordnet und sichtbar.
  4. 1999XP: User Stories und Abnahmekriterien, die sagen, wann eine fertig ist.
  5. 2007Kanban für Software: ein Board, das zeigt, was in Arbeit ist.
  6. 2011ADRs, Michael Nygard: eine kurze Datei pro Architekturentscheidung.
  7. jetztCoding-Agenten: Jeder Schritt dauert Minuten. Ohne die Artefakte beginnt jede Sitzung leer.

Ist das ein Memory-Plugin?

Nein. Ein Memory-Plugin merkt sich, was der Agent gesagt hat. ProjectStore hält fest, was das Projekt entschieden hat, als reviewte Dokumente mit Status und Datum. Neue Arbeit läuft dann über diese Dokumente. Der Unterschied zeigt sich, wenn du Agent, Rechner oder Teammitglied wechselst: Ein Gedächtnis gehört zu einem Agenten, einem Nutzer oder einem Rechner, und selbst ein in git abgelegtes Gedächtnis besteht aus den eigenen Notizen des Agenten; der Vault ist die Projektakte – freigegeben, reviewt, mit Status – und wird über git weitergegeben.

Brauche ich Obsidian?

Nein. Der Vault ist ein gewöhnlicher Ordner mit Markdown-Dateien. Öffne ihn in einem Editor, sieh ihn dir auf GitHub an oder nutze Obsidian, wenn dir dessen Graph und Board gefallen. Auch ohne das Plugin bleiben die Dateien genauso lesbar.

Schreibt es jemals, ohne zu fragen?

Nein. Jede neue Datei und jede Änderung wird dir zuerst gezeigt, mit Pfad und vollständigem Text. Dann wartet ProjectStore auf „Ja“, „Vor dem Speichern bearbeiten“ oder „Nein“. Die Helfer, die das Gespräch beobachten, schlagen nur einen Befehl vor. Der einzige Agent, der schreiben kann, der Clerk, läuft nach deinem Ja und speichert genau das, was du freigegeben hast.

Was bleibt, wenn ich es entferne?

Dein Vault, unverändert: Er ist reines Markdown in einem eigenen Git-Repository. Die Bindung des Projekts und die Agentenmodelle des Teams bleiben ebenfalls, sodass ein erneutes Setup sie wiederfindet. Das Codex-Plugin ist für jedes Projekt auf dem Rechner registriert, deshalb ist seine Entfernung ein eigener Schritt. So entfernst du es
