Ваш агент пише код. ProjectStore веде записи.

Що вирішено, що в роботі, що перевірено — як рецензований Markdown у git, який може прочитати будь-який агент і будь-хто з доступом до репозиторію.

01 / Встановлення

Просто попросіть агента: Claude Code · Codex · Gemini CLI · Cursor

Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.

У Claude Code цей промпт додає git-маркетплейс і встановлює з нього; увімкніть його автооновлення в /plugin. У Codex натомість запустіть команду нижче: усередині сесії встановлення чекає на термінал. Для інших агентів плагіна поки немає; вони читають той самий vault через його файли, CLI та MCP.

Або запустіть у терміналі: у вашому проєкті, поза агентом

~/your-project $
npx projectstore setup

02 / Далі просто говоріть

Жодних команд вчити не треба. Просто говоріть.

Скажіть, що вам потрібно. Агент веде робочий процес, показує кожну чернетку й питає, перш ніж записати. Сцени нижче — з Claude Code.

1Рішення

Вирішили раз — «чому» лишається.

Рішення стає ADR із відхиленими альтернативами. Без вашого «Так» нічого не записується, а потім ADR рецензує critic із чистим контекстом.

2План

Плани одразу мають критерії приймання.

Прогалини помічають, поки це ще речення, а не баги.

3Розробка

«Готово» означає «доведено».

Planner каже, де місце зміни. Reviewer просить доказ для кожного критерію приймання, перш ніж сторі закриється.

4Наступна сесія

Завтра починається з дошки.

Нова сесія відкривається з тим, що зараз у роботі. Назвіть сторі — і агент прочитає його план і чекліст із файлу.

Налаштування — теж речення.

смугаClaude Code · експериментально

«Покажи проєкт над моїм промптом.»

Епік, у якому ви працюєте, наскільки він просунувся, його мета, ваше сторі й агент за роботою — над промптом, поки ви працюєте. Поки смуга видна, рядок стану поступається їй місцем.

моделіClaude Code · Codex: лише моделі

«Запусти critic на Fable і покажи ProjectStore у моєму рядку стану.»

агент виконує:

npx projectstore configure --set agents.critic=fable --set statusline=on
ваш власний skillClaude Code · Codex: файли та CLI

«Напиши skill: перед релізом перелічувати незавершені сторі та ADR, які ще чекають на рев’ю.»

Звичайний skill, що читає записи проєкту: простий Markdown із frontmatter або 8 MCP-інструментів лише для читання.

Усі налаштування — з термінала:
npx projectstore configure

Як оновити й як видалити — у README, розділи Upgrading і Uninstalling. Після видалення vault лишається.

04 / Де його місце

Не пам’ять агента. Не конвеєр специфікацій.
Проєктні артефакти.

06 / Наодинці чи командою

Один vault. Багато сесій, людей і агентів.

Кілька сесій, один vault

Два агенти чи двоє людей в одному vault одночасно — це нормально. Кожна сесія знає про інші, а кілька простих правил не дають їм заважати одна одній.

Кожен бачить більше, ніж свою частину.

Розробник, техлід і QA працюють з одними й тими самими рішеннями та критеріями. Людині без агента потрібен лише GitHub або редактор Markdown: це просто файли.

Спільні контракти. Окремі ділянки роботи.

В одному проєкті команди API, Web і Platform ведуть власні епіки на основі спільних ADR і специфікацій. Зміну спільного контракту обговорюють на рев’ю з командами, які ним користуються. ProjectStore показує, які сторі від нього залежать.

Різні агенти. Спільна основа.

Планувальник читає рішення і мапу коду. Виконавець — сторі та специфікацію. Рев’юер — диф і критерії. Кожен отримує потрібний йому контекст, а не всю історію чужої сесії. Сесії в одному vault попереджають одна одну.

07 / Метод, докази й запитання

Індустрія давно це винайшла.
Агенти зробили це дешевим.

ADR, рев’ю, беклог, критерії приймання, зв’язки від мети до коду. Зрілі інженерні команди працюють так уже двадцять років. ProjectStore нічого з цього не вигадує.

  1. 1969RFC: рішення записані й пронумеровані, а потім відкрито обговорені.
  2. 1992DO-178B: в авіоніці кожна вимога має простежуватися до коду і до тесту.
  3. 1995Scrum: робота як беклог, упорядкований і видимий.
  4. 1999XP: користувацькі історії (user stories) і критерії приймання, що кажуть, коли історія готова.
  5. 2007Канбан для ПЗ: дошка, що показує, що в роботі.
  6. 2011ADR, Майкл Найгард: один короткий файл на одне архітектурне рішення.
  7. теперАгенти, що пишуть код: кожен крок займає хвилини. Без артефактів кожна сесія починається з нуля.

Це плагін пам’яті?

Ні. Плагін пам’яті запам’ятовує, що сказав агент. ProjectStore фіксує, що вирішив проєкт, у документах зі статусом і датою, які пройшли рев’ю. Нова робота потім іде через ці документи. Різниця помітна, коли робота переходить до іншого агента, на іншу машину чи до іншого колеги: пам’ять належить агентові, користувачеві чи машині, і навіть пам’ять, що зберігається в git, — це власні нотатки агента; vault — це записи проєкту — схвалені, рецензовані, зі статусом, — і він передається через git.

Чи потрібен Obsidian?

Ні. Vault — це звичайна тека з Markdown-файлами. Відкривайте її в редакторі, переглядайте на GitHub або користуйтеся Obsidian, якщо вам подобаються його граф і дошка. Без плагіна файли так само легко читати.

Чи записує ProjectStore щось без дозволу?

Ні. Кожен новий файл чи правку вам спершу показують — зі шляхом і повним текстом. Потім ProjectStore чекає на «Так», «Редагувати перед збереженням» або «Ні». Помічники, що стежать за розмовою, лише пропонують команду. Єдиний агент із правом запису — clerk — запускається після вашого «Так» і зберігає саме те, що ви схвалили.

Що залишиться, якщо його видалити?

Ваш vault лишається недоторканим: це звичайний Markdown у власному git-репозиторії. Прив'язка проєкту й моделі агентів команди теж лишаються, тож повторне встановлення їх знайде. Плагін Codex зареєстровано для всіх проєктів на машині, тому його видалення — окремий крок. Як видалити
