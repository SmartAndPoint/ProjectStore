Um método e um plugin para Claude Code e Codex

Um método para trabalhar com agentes de IA que realmente funciona.

ProjectStore é um método e um framework para criar apps e serviços de qualquer tamanho com agentes de IA.

Antes de tudo, é uma forma de uma pessoa e agentes trabalharem juntos. Você decide o que construir. Um agente escreve o plano, um segundo agente procura falhas nele, e você aprova. Depois o agente constrói, e um terceiro confere o resultado com a sua lista de verificação, item por item.

Ele é instalado como plugin no Claude Code e no Codex. A partir daí você conversa com o agente com as suas próprias palavras, e ele guarda as decisões, os planos e o progresso como arquivos simples no seu projeto. Amanhã, em outra máquina ou em outro agente, o trabalho continua de onde parou.

Instalar Como funciona

Funciona no Claude Code e no Codex. OpenCode em breve; Gemini, Z.ai e DeepSeek em seguida.

Por que funciona
  • O reviewer não fecha a tarefa até que todos os pontos da lista de verificação estejam marcados.
  • A sessão começa pelo quadro de tarefas e pela história em andamento.
  • A decisão fica registrada com o seu motivo, e o agente a segue.
  • O Codex lê os mesmos arquivos e continua.
  • Toda decisão tem um arquivo com o motivo e as opções que você descartou.

Instalação e primeiros passos

Você pode começar mesmo que não seja programador.

O seu agente roda os comandos por você. Você instala dois programas, abre uma pasta de projeto e cola uma frase.

Início rápido

  1. Consiga um agente

    Um agente é um programa que escreve e executa código a partir das suas palavras. Qualquer um serve: Claude (o app, a aba Code) ou Codex, da OpenAI.

  2. Instale o Node.js e abra uma pasta de projeto

    O Node.js é a base em que o ProjectStore roda: o instalador LTS de nodejs.org, versão 20 ou mais nova, no macOS ou no Linux. Crie uma pasta vazia, por exemplo “my-bot”, e abra-a no agente.

  3. Instale o ProjectStore

    Peça ao seu agente ou rode o comando em um terminal, na pasta do projeto.

    Install the projectstore plugin from https://github.com/SmartAndPoint/ProjectStore and set it up for this project.
    ~/your-project $
    npx projectstore setup

    Depois de instalar, reinicie o agente; o Codex pede uma vez para aprovar os hooks dele.

  4. Diga o que você quer construir

    I want to create a stock trading bot

    «Quero criar um bot para negociar ações»

  5. Responda às perguntas dele

    O agente pergunta o que só você pode decidir, antes de planejar:

    The project is empty—no code, and the vault just has README scaffolding with no epics, stories, or ADRs yet. Per CLAUDE.md, I'll start with an epic and its stories in the vault rather than code, but first I need you to make a few decisions that will shape the plan.

    Tradução: «O projeto está vazio, ainda não há código nem notas. Vou começar pelo plano, não pelo código. Mas primeiro preciso das suas decisões».

    Should the bot trade real money? (negociar com dinheiro real?)

    1. Paper only (Recommended) · conta de simulação/sandbox
    2. Backtest only · dados históricos, sem corretora
    3. Live, with safeguards · parada de emergência, limites de posição, teto de perda diária

    De uma sessão real do Claude Code em um projeto vazio, 21 de outubro de 2026. O texto do agente é citado palavra por palavra; os detalhes das opções foram encurtados.

  6. Aprove o plano

    A essa altura o critic já o conferiu. Depois do seu sim, o agente constrói, e o reviewer confere o resultado com a lista de verificação.

Como funciona

Um ciclo com uma checagem independente dentro.

Agentes escrevem código rápido e, com a mesma rapidez, decidem de novo questões já resolvidas: toda sessão nova chega vazia. A solução não é um agente mais esperto. É reunir contexto → agir → verificar, aplicado ao projeto e não só ao código.

Os agentes

6 agentes. Cada um resolve só a sua própria tarefa.

Os consultores verificam, planejam e organizam, sem mudar nada. Um único clerk salva só o que você aprovou, depois do seu Sim.

criticsomente leitura · independente

Depois que alguém escreve ou altera um ADR, uma spec, um épico, uma história ou um design

Procura pontos fracos, confere cada afirmação com a fonte e pergunta como o plano pode dar errado. Sem bajulação.

opus · max
plannersomente leitura · independente

Antes de começar o trabalho em uma história (story plan)

Vê onde os épicos anteriores estão no código. Diz onde a mudança deve ficar, o que reaproveitar, com o que tomar cuidado e em que ordem trabalhar.

opus · max
reviewersomente leitura · independente

Depois do código, antes do commit ou do story close

Pede evidência para cada critério de aceitação, inclusive os da spec. Depois verifica corretude, regressões e testes.

opus · max
librariansomente leitura · sugere

De tempos em tempos, antes de releases, depois que o vault cresce rápido

Encontra o que nenhuma regra pega: notas de pesquisa que contradizem um ADR aceito, duplicatas, vínculos faltando, documentos prontos para arquivamento.

opus · max
archaeologistsomente leitura · sugere

Uma vez, depois de vincular uma base de código existente

Encontra decisões que ninguém registrou, no código, nos arquivos de configuração e no histórico do git. Sugere ADRs para elas, com evidência.

opus · max
clerkgrava · depois do seu Sim

Só dentro do fluxo de um comando, só depois do seu Sim

Salva exatamente o que você aprovou, nada mais. Depois reconstrói o quadro e roda as verificações. Não escreve nada por conta própria e não pergunta nada.

Os modelos padrão são os do Claude Code. No Codex, cada papel é uma skill de mesmo nome que pede ao Codex para iniciar o papel, como $projectstore-critic para o critic; ele usa o modelo da sessão, a menos que você defina outro.

As proteções

Mecanismos sustentam o processo, não a disciplina.

Sem história, um lembrete

Um agente que começa a editar código sem nenhuma história aberta é lembrado de abrir uma. Uma mudança do tamanho de uma funcionalidade começa no vault.

O que não foi revisado fica marcado

Um artefato que precisa de revisão leva review_status: pending até que uma rodada do critic seja aplicada. “Ainda não revisado” é um estado que as ferramentas conseguem ler, não algo de que alguém precise se lembrar.

Um doctor sem IA

O doctor verifica de forma determinística a consistência mecânica do vault. No CI, roda sem agente e sem tokens.

Onde olhar, gerado

O graph.md guarda os vínculos de cada artefato nos dois sentidos; o code-map.md diz onde está o código de cada épico. Antes de uma escolha de arquitetura, o agente é levado primeiro ao índice de ADRs.

Depois do /compact, o vault volta

No Claude Code, depois de um /compact executado por você, a sessão recomeça com a orientação do vault e com os arquivos do vault que a conversa tocou antes dele.

Uma segunda sessão é avisada

Uma sessão que começa enquanto outra trabalha no mesmo vault abre com um aviso de várias sessões: busque antes de criar qualquer coisa nova.

Pronto quer dizer provado

Uma história fecha com evidência sob cada critério.

O planner disse onde a mudança deve ficar antes do código, e o plano entrou na história com o seu sim; o reviewer conferiu o diff com cada critério depois. Cada linha de prova é um teste, um comando que rodou ou uma linha de código.

Qualquer agente pode ler este registro, com ou sem o plugin: pela CLI, que responde em JSON e não gasta tokens, ou pelas 8 ferramentas somente leitura do servidor MCP.

Letras miúdas

Letras miúdas

  • Rodar o ciclo gasta tokens: os rascunhos, o critic e o reviewer rodam no modelo que você já paga. O README mede isso.
  • No Claude Code, o critic e o reviewer são agentes separados, de contexto limpo. No Codex, os papéis são skills.
  • O ProjectStore é contexto compartilhado do projeto e uma forma de trabalhar. Não é um orquestrador de agentes: iniciar agentes é tarefa do seu harness.
Equipe e muitas sessões

Muitas sessões. Muitas pessoas. Um vault.

O contexto pertence à equipe, não ao chat de um desenvolvedor. ADRs e specs passam por pull requests, como o código. O que se revisa é o raciocínio.

Quatro formas de trabalhar

Quatro formas de trabalhar

Várias sessões, um vault

Dois agentes ou duas pessoas no mesmo vault ao mesmo tempo é algo normal. Cada sessão sabe das outras, e algumas regras simples evitam que uma atrapalhe a outra.

  • Nada é sobrescrito em silêncio. Antes de salvar um arquivo novo, o ProjectStore verifica se ele já existe. Duas sessões sobre o mesmo tema geram um conflito, não duas cópias.
  • Cada linha de status mostra o próprio trabalho. 2–6 sessões lado a lado veem, cada uma, exatamente o próprio épico e a própria história.
  • Nomes de sessão são sugeridos, não impostos. Quando uma sessão se concentra em um único trabalho, ela recebe a sugestão de um nome. Raramente: no máximo duas vezes por sessão, 12 sugestões em nove sessões registradas.

Todos enxergam mais do que a própria parte.

O desenvolvedor, o tech lead e o QA trabalham a partir das mesmas decisões e dos mesmos critérios. Quem não usa agente só precisa do GitHub ou de um editor de Markdown: são apenas arquivos.

O contexto está disponível para a equipe toda, não só para o dono do chat.

Contratos compartilhados. Áreas de trabalho separadas.

Em um mesmo projeto, as equipes de API, Web e Plataforma conduzem seus próprios épicos com base em ADRs e specs compartilhados. Uma mudança em um contrato compartilhado é discutida na revisão com as equipes que o usam. O ProjectStore mostra quais histórias dependem dele.

Quem é dono de quais artefatos e quem aprova os contratos é decisão da equipe.

Executores diferentes. Base comum.

O planejador lê as decisões e o mapa de código. O implementador lê a história e a spec. O revisor lê o diff e os critérios. Cada um recebe o contexto de que precisa, não todo o histórico da sessão de outro. Sessões no mesmo vault avisam umas às outras.

Iniciar agentes e passar trabalho entre eles é tarefa do seu harness ou orquestrador.

A indústria inventou isso há muito tempo.
Os agentes tornaram isso barato.

ADRs, revisões, backlog, critérios de aceitação, vínculos do objetivo ao código. Equipes de engenharia maduras trabalham assim há vinte anos. O ProjectStore não inventa nada disso.

A parte cara

O processo sempre foi valioso. O que custava caro era ter pessoas executando cada passo.

o processo das pessoas+a velocidade dos agentes=ProjectStore

O ProjectStore junta as duas coisas. A velocidade dos agentes torna o velho processo barato pela primeira vez. Os documentos desse processo, guardados em arquivos ao lado do código, dão aos agentes o que eles nunca tiveram: o contexto do projeto, com vínculos para cima, até os objetivos, e para baixo, até o código. A regra é que cada passo seja revisado por um segundo agente, que não escreveu o rascunho. A velocidade ganha memória, e a memória ganha verificação.
