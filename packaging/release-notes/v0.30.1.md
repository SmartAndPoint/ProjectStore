# v0.30.1 — Configure changes any setting after setup

Setup asks only what a first install needs. From 0.30.1, one command changes everything after it. A status line wired from a terminal is now kept current. The README, the docs, the site and the first-run welcome tell the same story of install, configure and removal.

## Configure

From a terminal in your project:

```
npx projectstore@0.30.1 configure
```

It shows every setting with its current value and where it lives:
- each agent's model, per harness;
- the status line and the band above the prompt (Claude Code);
- the vault's template language, the default author and tags;
- the vault's spec policy and lifecycle gates.

At a terminal it asks which to change, then shows one plan and asks once. Without a terminal it prints the same view and writes nothing. To change a setting there, name it with `--set`; naming it is the confirmation:

```
npx projectstore@0.30.1 configure --set agents.critic=fable --set statusline=on
```

`--dry-run` shows the plan and writes nothing, and `--json` returns the settings as one envelope. In a project that uses two harnesses, `--harness <id>` picks whose agents a model change applies to.

Each setting has exactly one writer, and the plan says which file it changes:
- **The agents' models** live in `.projectstore/harness/<harness>.json`. That file is committed, so a change there is a team change.
- **The status line, the band, the language and the other binding keys** live in `.projectstore/projectstore.json`, which stays on this machine.
- **The spec policy and the lifecycle gates** live in the vault's `.projectstore.json`, which commits with the vault. Setting `spec_policy=required` records when it took effect, and stories closed before then are exempt.

In a Claude Code session, the status-line and bind commands now preview the change and write it through configure; they no longer write the files themselves. The agents command's configure shares configure's writer and prints what it printed before.

## The status line keeps its flag

Installing the status line surface from a terminal now records that the line is on, and uninstalling it records that it is off. Before, later plans skipped a line wired that way as if you had opted out, so upgrades did not keep it current.

## One account of install, configure and removal

- **README.** What setup needs: Node.js 20 or later; npm, for Codex only; the agent's own CLI; a terminal outside every agent session; macOS or Linux. Other package runners start setup the same way: bunx, pnpm dlx and deno. A new Configure section. Uninstalling now says what a removal keeps (the vault, the binding, the committed agent models, and Codex's user-wide registration until `--global`) and how to reinstall clean.
- **Docs.** Getting started leads with setup. The harnesses page covers configure for Codex.
- **The site,** in all eight languages, adds the runners, configure, links to upgrading and removal, and a FAQ entry on what a removal keeps.
- **The welcome follows how you installed.** In Claude Code, an npm registration's first-run welcome names the npm upgrade. A git-marketplace copy keeps the auto-update advice.

## Upgrading

From npm, from a terminal in your project:

```
npx projectstore@0.30.1 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.1 upgrade --harness codex
```

From the git marketplace, in Claude Code:

```
/plugin update
```

Then restart the agent. The binding, the overlays and the vault's config are untouched.

**A status line you wired from a terminal before 0.30.1** has no flag, so upgrades leave its launcher stale. It still renders. Record the flag once, which also re-stamps it:

```
npx projectstore@0.30.1 configure --set statusline=on
```

On the pre-0.28 layout, configure and the status-line command refuse until the project moves. Doctor names the upgrade that moves it.

Codex stays **experimental**, as [docs/harnesses.md](https://github.com/SmartAndPoint/ProjectStore/blob/main/docs/harnesses.md) defines it.
