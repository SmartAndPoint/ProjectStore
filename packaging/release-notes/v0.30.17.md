# v0.30.17 — status changes are stamped and logged, and a creation says a neighbour's row may drop

This release has four changes. Every status change a gate or a verb makes is now stamped and logged in the story. A new `move` verb takes a story between `planned` and `todo`. `configure` no longer writes an email address into a person's git names. And every creation's approval now also says that a row another session just added may drop for a while.

## Status stamps and the status log

Every status change a gate or a verb makes now stamps `status_changed_at` and appends one line to the story's new `## Status log`:

```
- <ISO> status: from → to — reason (actor)
```

The actor is the gate or verb that made the change, not a person: one of `plan gate`, `close gate`, `follow`, `groom`, `handover`, `move`. The gate script takes `--reason` and `--actor` for verbs that come later. `/projectstore:story plan` and `close` pass neither, so their lines read `work started (plan gate)` and `closed (close gate)`. A hand edit of `status:` leaves the stamp untrusted until the next logged change. The move to `review` is still such an edit: no gate or verb makes it yet, so a story in review carries an untrusted stamp until its next logged change. The changes logged in 0.30.17 are the plan gate's move to in-progress, the close gate's move to done, and `move` between `planned` and `todo`.

On the move to in-progress, the plan gate sets the assignee to the binding's `default_author`, when one is set and differs, and logs it as its own `assignee:` line. So a story assigned to one person and started from another person's session becomes the second person's. The story's header rows for Status and Assignee follow the frontmatter on each change.

The plan and close ceremonies also update the Status cell of the story's row in the epic's Stories table, when that table has a Status column and a row that links to the story. With no such row, the command says `epic-row-missing` and leaves the epic alone. An epic whose stories are a numbered list, or whose rows carry plain titles, is not touched.

Two behaviour changes come with it:

- The gates compare statuses through the board's aliases now, so they no longer rewrite a status written as an alias the board knows. The plan gate leaves `in progress` and `closed` as they are (0.30.16 reopened a `closed` story as in-progress). The close gate leaves `closed` as it is (0.30.16 rewrote it to `done`).
- A status named like a built-in property (for example `constructor`) now lands in Backlog, like any unknown status. Before, such a story fell off the board.

Nothing reads the age of a status yet. Doctor's flow checks start reading it in a later release.

## `move`: a story is readied

A new `move` verb takes a story from `planned` to `todo` and back. The story is named `<EPIC-ID>/<story-id>`. For example:

```
npx projectstore@0.30.17 move PS-CORE/story-x todo --reason "ready for the next week" --write
```

Without `--write` it prints what it would do. At a terminal, `--write` asks first. Without `--reason` it exits 2. In a session, `/projectstore:story ready` is its command form. It also updates the story's row in the epic's Stories table, under the same rule as the gates. After the story is written, `move` regenerates the derived views. If one could not be regenerated, `move` names it and why, and the same command run again finishes the job.

## Git names take no addresses

`configure --set 'flow.people[<name>].git_names=…'` now refuses an entry that is an email address or holds one, including the `Name <address>` form that `git log` prints. The error message does not repeat the value. A name with an `@` that is not an address, like `me@laptop`, is still accepted.

`configure` no longer writes an address into `git_names`. One already there, because 0.30.16 took any text there or because someone wrote it by hand, stays: nothing removes it, and the configure view prints it as stored. Set the key again with names only, or clear it with `-`. The plan of that change shows the old value once.

## A creation's approval names the concurrent-row case

When you create an ADR, epic, spec, research, concept, meeting or runbook, one approval covers both the artifact and the regeneration of its folder's index. The question already said that the regeneration rewrites the whole table, so a creation may also fix a stale row for another artifact. Now it also says the other side: the regeneration may drop, for a while, a row another session added a moment before, and the next regeneration of that folder's index restores it.

The commands now say what contract 2 of the spec "Creation-time index updates are regenerations, not appends" asks. Contract 2 now quotes the sentence, contracts 2 and 6 no longer call the preview advisory, and a test checks the sentence in all seven commands. The reviewer's first spec-drift run found this gap.

## Upgrading

Nothing migrates and no state moves. Existing stories get a Status log on their next transition. Until then they carry no trusted stamp, and their age falls back to `updated`. If you set `git_names` under 0.30.16, check `<vault>/.projectstore.json` for an address. Removing it there does not remove it from the vault's git history. The agents block stays v5. Codex's skills change, so Codex needs its own upgrade, below.

From npm, from a terminal in your project:

```
npx projectstore@0.30.17 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.17 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```
