# v0.30.16 — the reviewer checks a spec against the code, and the vault declares its flow policy

This release brings two things. The reviewer can now check an active spec against the code and say where they drifted apart. And the vault can store a flow policy, for checks that come in later releases.

## Spec drift

The reviewer checks a story's diff before the story closes. Until now nothing checked a spec later, when another story or a plain commit has changed the code since.

Ask the reviewer for spec drift on a named spec. It first runs a new read-only script, `scripts/spec-drift.mjs <spec>`, which prints the facts as JSON:

- each contract with its markers, whether it was removed, and its anchor: the date of its last valid marker, else the spec's `date:` (`--since <date>` overrides);
- the stories the spec covers, with their status and `code_refs`, and any empty or missing refs;
- the files those refs expand to, as source, tests or surface, with line counts and the commits since each anchor;
- the files citing each contract;
- the scan status: `ok`, `no-git` or `unknown`.

A spec that is not `active` exits 1.

Then the reviewer reads the code:

- **Budget.** When the spec has more than 8 contracts that are not removed, or more than the budget you name, it gives you the size and the contract list and asks which contracts to check. On this project that is the usual first answer: most specs have more.
- **Verdicts.** Each contract it checks gets one of three:
  - `holds`, with a line of code quoted verbatim;
  - `drifted`, with the line that contradicts the contract, or the search that found nothing when something named is gone;
  - `cannot tell`, with the reason.
- **Proposals.** Each drift comes with a proposal: an amendment marker for an open story to carry, or a follow-up story. The reviewer writes nothing.

`docs/contracts-and-tests.md` has a section on it. It is meant for a spec whose covered code changed since its anchor, not for every release. A large spec's bundle runs to tens or hundreds of kilobytes, which may exceed what a host shows of one command's output; we have not yet seen how a host handles that.

## Flow policy

The vault's `.projectstore.json` can hold a `flow` block:

- each person's time on the project, which sets their WIP limit unless they have a `wip` of their own;
- age thresholds for review, idle work in progress and ToDo;
- the windows for throughput and capacity.

0.30.16 only stores and shows this policy. Nothing reads it yet: doctor, `next` and the band start checking against it in later releases.

`configure --set` writes it, for example:

```
npx projectstore@0.30.16 configure --set flow.wip.full=3 --set 'flow.people[First Last].time=full'
```

A person is named the way stories write their assignee, never by an email address. Their name, git author names, time share and the date they left commit with the vault. No key has a default in code. The key list is in `docs/extending.md`. The menu does not show these keys. The configure view shows a "Flow policy" group while any is set.

The vault config writer now merges nested keys, so a change under `flow` keeps the rest of the block.

## Upgrading

Nothing migrates and no state moves. The agents block stays v5. Codex's reviewer skill changes, so Codex needs its own upgrade, below.

From npm, from a terminal in your project:

```
npx projectstore@0.30.16 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.16 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```
