# v0.30.24 — a dashboard write that lands when the views cannot be rebuilt, an initiative decided from the page, and assign

This release has three pull requests (#189, #190, #192). On a vault where the core cannot rebuild the derived views in the page's copy, every write of the 0.30.23 dashboard but a reorder made nothing; now it lands. The page decides an initiative and sets an epic's initiative, and the core gains `assign`, which names who holds a story in ToDo.

```
npx projectstore@0.30.24 dashboard
```

## A write lands when the views cannot be rebuilt

After each write, the core rebuilds the derived views (the board, the folder lists, the code map, the graph) in the page's own copy of the vault. When that failed, the core still wrote the item but exited with an error, and the 0.30.23 page threw the whole change away; after New it showed only "left: the derived views", with no reason. The page never commits those views anyway, so now it commits what the verb wrote and says, with the core's reason, that the views were not rebuilt in its copy. This covers New, a move, an editor Save, Hand over and the initiative and epic rows. A refusal now also shows the reason the core gave for each thing it left, not only its first words.

If you saw "left: the derived views", upgrade and try again: the note after the change gives the core's reason, or says the core gave none. Please tell us what it says in an issue at https://github.com/SmartAndPoint/ProjectStore/issues, since we do not yet know why the views fail on those vaults.

## Decide an initiative and set an epic's initiative from the page

An initiative's side panel has **Accept…**, **Reject…** and **Defer…**, each asking for one line of why, and **Edit fields…** for its title, owner and priority. An epic's side panel has **Set initiative…** (or **Change initiative…**) and **No initiative…**. The ⌘K palette has the same lines. Each runs the core's `initiative` or `epic` in the page's clone, with a preview of what changes, and the click is the approval. **Edit fields…** starts from the item's values and sends only a field you changed, so a value the page shows but the file does not hold is never written by being left alone. An epic dragged into another initiative's group still goes back to its place; its note now points at the epic's own button.

## assign: who holds a story in ToDo

```
npx projectstore assign PS-CORE/story-faster-login "Ann Lee" --reason "next up"
npx projectstore assign PS-CORE/story-faster-login --clear --reason "nobody yet"
```

`assign` names the holder of a story in ToDo, or clears the holder of one in the Backlog or ToDo. Bare, it prints the plan; `--write` writes the story's `assignee:`, its Assignee row and one line in its Status log, and moves no date and no review mark. A story in the Backlog is refused with `move … todo` to run first, started work with `handover`, and a done, set aside or unknown status is refused as such. An agent is a name that starts with `agent:`; when its load, its started stories plus its stories in ToDo, is at the WIP limit of the vault's flow policy, `assign` refuses it, counted again just before the write. A person at the limit is warned and assigned. An agent the flow policy gives no limit is assigned with a note that says so, and a vault with no `flow` block checks no limit.

## What it runs, writes and sends

- The page runs the core's `initiative` and `epic` in its clone through the same Node, as it runs `move`.
- A write whose only failure is the derived views commits the files the verb wrote, never a view, as every write of the page does.
- `assign` writes one story file and its session record entry, and refreshes the derived views, as `handover` does.
- Nothing new is sent: the page commits in its clone, and only **Publish for review…** pushes.

## Upgrading

Nothing migrates. What changes when you upgrade:

- stop a running dashboard and start it again: an older server keeps serving its own older page;
- a write on the page that 0.30.23 refused with "left: the derived views" now lands, with a note;
- the dashboard's clone in `.projectstore/state/dashboard/` is used as it is, with its kept branches;
- an npm copy fetches the dashboard's package for 0.30.24 on its first `dashboard` run, into `dashboard/0.30.24/` beside the old version's folder, which stays;
- `assign` is new; its lines in a Status log end with `(assign)`, and an older copy reads them like any other line.

The commands, agents and hooks are the same. An installed copy needs the upgrade for `assign`.

From npm, from a terminal in your project:

```
npx projectstore@0.30.24 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.24 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```

The marketplace serves the main branch, but the plugin's version is pinned, so a copy installed or updated since #189 merged may already have some of these changes under the number 0.30.23, and a copy that was already at 0.30.23 gets them only with 0.30.24.

## Not seen live

- The write that lands when the views fail is checked in tests and on the packed page where a folder takes the board's place; the vault where it was seen is not tried, and why its views fail is not known yet.
- Hand over and Edit fields with the views failing are run on the packed page, not in the page's tests.
- The note after such a write is checked in the page's tests, not seen in a browser; the packed page of this release is not opened in one.
- On Windows the page still reads only: none of these writes is offered there.
- `assign` with an agent at its limit is checked in tests; no vault here has a `flow` block.
