# v0.30.9 — the MCP server's entry names no variable but the plugin root, and tests can cite a spec's contracts

This release answers the one finding that blocked 0.30.8 in Anthropic's plugin directory: the line that starts the MCP server named a variable the portal does not allow there. The server serves the same tools to the same project; only the way it learns the project changes. The release also lets a spec's contracts carry scenarios and lets tests cite them, so doctor can say which contracts no test covers.

## The MCP server's entry names only the plugin root

The developer portal validated 0.30.8's `directory` branch and blocked it on one finding, `COMMAND_PATH_COMPUTED`. The server's entry in `.mcp.json` passed the project as `--project ${CLAUDE_PROJECT_DIR}`, and the portal blocks any variable but `${CLAUDE_PLUGIN_ROOT}` in a server's command. The entry is now `node ${CLAUDE_PLUGIN_ROOT}/scripts/mcp-server.mjs`, with no other argument and no `env`.

The server still finds the project. Claude Code exports `CLAUDE_PROJECT_DIR` into the server's environment, and the server reads it there, ahead of `PROJECTSTORE_PROJECT_DIR`, the same order 0.30.8's `--project` gave. A host that exports no `CLAUDE_PROJECT_DIR`, with no `PROJECTSTORE_PROJECT_DIR` set either, gets a refusal that says to pass `--project` or set `PROJECTSTORE_PROJECT_DIR`, instead of a server. A headless Claude Code run with the plugin loaded from its folder connected the server, and its `status` tool answered for the bound project.

`npx projectstore mcp --project .`, for a host without a plugin channel, works as before: `--project` first, then `PROJECTSTORE_PROJECT_DIR`, then the host's own project variable.

The portal does not publish its rules, so this fix answers what its report showed. The maintainer's Validate on the `directory` branch, once 0.30.9 is on it, is the proof.

## Specs: scenarios under a contract, tests that cite it, coverage in doctor

A spec's numbered contracts can now carry scenario items: list items that start with `WHEN`, `GIVEN`, `AND` or `THEN`. The keywords stay in English in every language, and the spec template shows them in all six. A contract that only a live run or a person can check is marked `(verified: live)` or `(verified: manual)`, and doctor does not count it as uncovered.

A test cites the contract it covers with a token in its name or in a comment beside it, such as `[example#3]`: the spec's id, or the short `alias` a spec may now set in its frontmatter, then the contract's number. `doctor --vault` finds the tokens with `git grep --untracked`, so a test not yet added to git counts too. For each active spec it reports how many contracts there are and, once a test cites one, which ones no test cites. It also reports a token that names no spec or no contract, a token that cites a superseded spec, a scenario without a `WHEN` or `GIVEN` or without a `THEN`, an alias two specs share, and, under lifecycle gates, a story's evidence that names a token no file carries. Doctor never runs a test.

The planner lists a contract's scenarios as the tests to write, each citing its contract. The reviewer reports a new test that covers a contract and cites nothing, and a cited test that does not assert the contract's outcome.

All of it is optional: a spec without scenarios, and a test without a citation, stay valid. [`docs/contracts-and-tests.md`](https://github.com/SmartAndPoint/ProjectStore/blob/main/docs/contracts-and-tests.md) shows how to write and cite a contract. The README's list of what ProjectStore runs now names doctor's `git grep --untracked`.

## For contributors: `npm run packlist` exits 0 again, and a command-paths row

`npm run packlist` had stopped with exit code 13. `packaging/shells.mjs` imported the version guard, which loads `shells.mjs` while its own top-level await is pending, so the two waited on each other. `packEntry` moves to `scripts/lib.mjs`, and a test runs the script in a copy of the repository: it must exit 0 and rewrite every packlist as committed.

`packaging/directory-guard.mjs` has a new row, `command-paths`. In a hook's `command` or `args` in `hooks/hooks.json`, or a server's `command`, `args` or `env` values in `.mcp.json`, it fails on a variable other than `${CLAUDE_PLUGIN_ROOT}`, a command substitution, a wildcard, an inline program such as `python3 -c`, or a path not written from `${CLAUDE_PLUGIN_ROOT}/`, by file and JSON path. It runs in CI and in `npm run release:check`, so 0.30.8's entry cannot come back unnoticed.

## Upgrading

Nothing to do on any channel beyond the usual update: nothing to migrate, no state moves, and the agents block stays v5. The new `.mcp.json` comes with the plugin, so there is nothing to edit by hand.

From npm, from a terminal in your project:

```
npx projectstore@0.30.9 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.9 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```
