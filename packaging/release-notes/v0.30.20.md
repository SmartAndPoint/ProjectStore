# v0.30.20 — the dashboard's page moves stories and sends them as one pull request

This release has one change. The dashboard's page can now write. You can move a story between the backlog and ToDo on the page, and send your moves to the vault's repository as one pull request. Nothing reaches the vault until a person merges that pull request.

```
npx projectstore@0.30.20 dashboard
```

## Moving stories from the page

Drag a story's card between the Backlog and ToDo columns of the board, or open the story and use its button. You give a reason in one line. The page first shows the move as ProjectStore plans it (the same plan `projectstore move` prints), and your click on the preview's button is the approval.

The page then runs ProjectStore's own `move` in its own clone of the vault's repository, and commits the change there: one commit per move, on a branch `dashboard/<you>/<time>` in that clone. The moves wait on that branch as one batch. The page never touches your own checkout, so it never picks up another session's uncommitted files. If the vault lives inside your code repository, the clone is the whole repository, and the pull request goes there.

- **Send** pushes the batch's branch to the vault repository's `origin`, under the same name, with your own git setup. Then it opens one pull request for it with your own `gh` login. A batch of one move takes that move's commit subject as the title; a bigger batch is called `Backlog changes from the dashboard (<n>)`. The body lists the moves, oldest first. When `gh` is missing or logged out, Send still pushes the branch and opens no pull request; the page says so, and the next Send asks `gh` again.
- **Discard** closes the batch's pull request, if one is open, and ends the batch. When `gh` cannot be asked, Discard ends the batch on this machine only, and an open pull request stays open on the code host until you close it there.
- **A merge is read on the next step.** When `dashboard` starts, when the page is opened, and when you choose "Fetch the vault's repository again" in the ⌘K palette, the page fetches its clone and asks `gh` about the pull request. Send and Discard ask `gh` first too. Once the pull request is merged (a merge commit, a squash or a rebase), a new batch starts from the default branch, and a move you made after Send is carried into it.
- **Kept branches.** A discarded batch, or a carry that hits a conflict, keeps its branch in the clone. The page lists it under **Kept branches** and never sends or deletes it. `dashboard/README.md` says how to send or delete one by hand.

Only `move` is on the page in this release. The other writes come later, one verb at a time.

## What the page shows while it can write

While the page can write, it shows the vault as its clone has it: `origin`'s default branch as last fetched, with your batch on top. Edits in your own checkout that are not on `origin`'s default branch do not show on the page. The page does not touch your checkout, so after your pull request is merged, pull in your own checkout of the vault to get the moves there:

```
git pull
```

A page that cannot write shows your checkout, as before.

## When the page can write

The page writes only on macOS and Linux, and only when:

- the vault is in a git repository with an `origin` remote;
- git gives an author name and email in that repository.

Otherwise it reads the vault and changes nothing, with no move controls, and its sidebar says why. The page needs git 2.30 or later; it does not check the version itself.

Pull requests need `gh`, logged in, and a repository on GitHub. On another code host Send pushes the branch and opens nothing, you open the merge request there yourself, and the page may not learn of the merge: use Discard to end the batch.

The first start makes the clone from `origin`, and the start waits up to 10 seconds for it. On a large repository or a slow network the page begins read-only and turns writable after its next refresh.

## What it runs, writes and sends

- **It runs git and `gh` on your machine,** with your own setup and login, only for the page. `gh`: `pr list`, `pr create` and `pr close`. git: in the vault's repository it only reads (the repository, its `origin`, a few settings, your identity); in the clone it clones, fetches, commits, merges the batch branch as `origin` has it, cherry-picks for the carry, resets and cleans; it pushes only the batch branch, `refs/heads/dashboard/…`. The README's section "What ProjectStore runs, writes, sends and fetches" lists every git command. No git hook runs in the clone, and nothing can stop to ask for a password: a push that needs one fails with git's message.
- **Only the page itself can make it write.** The server still listens on `127.0.0.1` only. The five write routes take POST, and only with the run's own token and the page's own `Origin`; a POST without both gets 403. Everything else still answers GET and HEAD only.
- **It writes under your project.** The clone and the page's own files live in your project's main checkout, under `.projectstore/state/dashboard/<you>/`, which git ignores; the page makes sure `.projectstore/.gitignore` lists `state/`. `<you>` is the binding's default author, written as a file name. Into the clone's own `.git/config` the page copies some settings from the vault's repository: `credential.*`, `url.*.insteadOf`, `url.*.pushInsteadOf`, `remote.origin.pushurl`, `core.sshCommand`, `ssh.variant`, the signing settings, and your identity. Some of these can carry a credential, for example a token inside an `insteadOf` address; the copies stay until you remove the clone.
- **Every step of the page puts the clone back** to its branch's last commit with `git reset --hard` and `git clean -d -x`, so an edit made by hand in the clone is lost. Make your own edits in your own checkout.
- **It sends** the batch branch and the pull request to the vault repository's own code host, and nothing else. The privacy page says the same.

The start line now says: "Nothing you do on it reaches the vault until a pull request you send from it is merged."

## Doctor

Doctor has a new note, `dashboard-kept-branch` (info). It names each branch the page keeps in its clone, with the number of its commits that the fetched default branch does not have: they may be work that was never sent. Doctor reads the clone on your machine and never fetches. `--fix` touches none of them. Sending or deleting a kept branch is your call. The batch that is still open is not a kept branch, so look at the page too before you delete the clone.

## Upgrading

Nothing migrates. What changes when you upgrade:

- the vault and your checkouts get no new file;
- the page now shows the clone, not your checkout, whenever it can write (see above);
- `.projectstore/state/dashboard/` appears on the first `dashboard` start whose checks pass, and stays until you delete it. Look at its open batch and kept branches before you delete it: they can hold moves you never sent;
- doctor's new note shows only when that folder holds a kept branch;
- an npm copy fetches the dashboard's package for 0.30.20 on its first `dashboard` run, into `dashboard/0.30.20/` beside the old version's folder, which stays.

The doctor command text changes, so an installed copy needs the upgrade to get it.

From npm, from a terminal in your project:

```
npx projectstore@0.30.20 upgrade
```

Codex's registration is per machine:

```
npx projectstore@0.30.20 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```

The git marketplace serves main, so a copy installed or updated since these changes merged may already have them under the number 0.30.19. For it, this release changes the number.

The agents block stays v5, and the MCP tools are the same nine.

## Not seen live yet, and known gaps

- One Send with the real `gh` from the published package. Send, Discard, the merge reading and the carry were checked against a local bare `origin` with a stub `gh`, and once from a checkout against a private GitHub repository (two moves sent, a squash merge, the carry, a second pull request discarded). The same run from `npx projectstore@0.30.20 dashboard` is done after this release.
- Windows: the page reads the vault and changes nothing. It was checked in tests only, not on a Windows machine.
- A core running main's code from a copy that is not a checkout can still take itself for an npm copy and fetch the page. A planned story covers it.
