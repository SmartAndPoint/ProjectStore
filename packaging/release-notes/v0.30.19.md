# v0.30.19 — a merged pull request closes its story, next and handover, and a dashboard over the vault

This release has four changes. A merged pull request can close its story. `next` picks the next task within your WIP limit, and the plan gate checks that limit. `handover` moves a leaving person's open stories to someone else. And a new verb, `projectstore dashboard`, opens a read-only page over the vault in your browser; a copy installed from npm fetches the page once per version.

## A merged pull request closes its story

```
/projectstore:follow
```

From a terminal:

```
npx projectstore@0.30.19 follow
```

A bare run prints a plan and writes nothing. `--write` writes it, after one question at a terminal. The slash command shows the plan, asks once, then runs `--write`. `--story <EPIC>/<id>` and `--pr <n|url>` narrow the run.

A story names its pull request in one of two ways. Either `external_refs.pr` in its front matter holds it, or a pull request in the same repository, into the default branch, has a `Closes-story: <EPIC>/<id>` line in its description. In the second case `--write` also records that pull request in `external_refs.pr`, with a `pr:` line in the Status log.

What a run does to a linked story:

- **Merged**: the story is closed through the same computation as the close gate. `closed_at`, `status_changed_at` and the Status log line are stamped at the pull request's `mergedAt`, or at the story's last Status log line when that is later, and a `Merged: <url> at <sha>, <mergedAt>.` line goes under the Final Summary. If doctor's story checks would still flag the closed story, for example an acceptance criterion with no evidence, it goes to review, or stays there, with the line "merged, awaiting evidence".
- **A story in review goes back to in progress** when its pull request is closed without a merge, is a draft again, or the review is older than `flow.age_days.review`, where the vault's policy sets it.
- **Ready for review**: a story in progress moves to review.
- **Only started work moves.** A story still planned or in ToDo is left as it is, with a `pr-before-plan` note. So is a story whose pull request merged into a branch other than the default one (`pr-merged-elsewhere`), and one reopened by hand after a close (`pr-merged-reopened`).
- **A story that a linked worktree of the vault's repository changed** is left for that branch, with a `story-on-branch` finding, and the run exits 1. The check runs with `--write` only.

After a write, `follow` sets the stories' rows in their epics, runs the epic rule and refreshes the derived views once.

**It runs `gh`**, the GitHub CLI, with your own login. It runs `gh pr view`, `gh pr list` and `gh repo view`, reads no token, and writes nothing to GitHub. No other verb runs `gh`. When `gh` is missing or logged out, `follow` says `gh-unavailable`, exits 1 and writes nothing. A project with no GitHub remote gets `pr-unreadable`. An `external_refs` that cannot be read counts as no link, and nothing says so.

Codex has the same flow as the new `projectstore-follow` skill.

## The next task, within the WIP limit

```
npx projectstore@0.30.19 next
```

`next [--assignee <name>]` answers what to work on, for the binding's default author unless you name someone. It only reads. Started work comes first: in progress, in review, and stories waiting for their close. New work from ToDo comes only while the person is under their WIP limit. At the limit, it says `at WIP limit <n>/<limit>`. When ToDo is empty, it lists the top five planned stories with the `move` command that puts each in ToDo. It exits 0 with an answer, 1 when the vault cannot be read, 2 on a usage error and 3 when the project is not bound.

The limit is in the vault's `flow` policy: `flow.people.<name>.wip`, or `flow.wip.full` or `flow.wip.part` by that person's `time`. With no limit set, nothing is held back.

**The plan gate checks it too.** `/projectstore:story plan` now reports the WIP count. When starting the story would put the assignee over the limit, it asks first, with No recommended. It asks under `lifecycle_gates: off` too. If you go ahead, the Status log line says "started over WIP limit <after>/<limit>". `/projectstore:status` now points to `next`.

## A leaving person's stories are handed over

```
npx projectstore@0.30.19 handover --from <name> --to <name> --reason "<why>"
```

A bare run prints the plan. `--write` writes it. `--story <EPIC>/<id>` moves one story only. Each open story of `--from` gets the new `assignee`, the new Assignee row and one Status log line: `assignee: <from> → <to> — handover: <reason> (handover)`. Its status and the status's stamp stay as they were.

It refuses:

- a `--to` marked as left in `flow.people`;
- a name that is empty or holds `@` or a control character;
- the same person as `--from` and `--to`;
- with `--story`, a story that is not `--from`'s, or is not open.

A name no story or policy uses gets a `person-unseen` note. The plan warns when `--to` would go over their WIP limit. A story that was reassigned to someone else meanwhile is left as it is, and the run exits 1.

**Doctor** has a new warning, `assignee-left`: a person with a `left` date in `flow.people` who still holds open stories. It comes with the handover command. Doctor never chooses `--to`. `flow-person-unknown` no longer fires for a person marked left, and `assignee-idle` now names the verb.

## The dashboard

```
npx projectstore@0.30.19 dashboard
```

The dashboard is a page over the project's vault in your browser: the backlog as initiative, epic and story, the board, the list, your own work, and each document with what links to it. It only reads the vault. It serves on `127.0.0.1`, on the first free port from 4800 to 4809, answers only GET and HEAD, and checks the `Host` header. It opens your browser only when you run it at a terminal. `--no-open` opens nothing. Ctrl+C stops it. `--port <n>` names the port, and a path after the verb names another project. Run it from a terminal, not inside an agent session: it serves until you stop it.

The page is a package of its own, `projectstore-dashboard`, released with ProjectStore, at the same version as the core. A copy installed from npm fetches it the first time it runs at a version, once:

- the package at exactly the running version, never another;
- from the registry your own npm is set to, with `npm install --ignore-scripts`, so no install script runs;
- into `~/.cache/projectstore/dashboard/<version>/`, or under `$XDG_CACHE_HOME/projectstore/` when that is set.

Later runs need no network. A checkout of the repository and the git marketplace's copy run their own `dashboard/` folder and fetch nothing.

When the fetch fails, `dashboard` exits 1 and says why:

- the version is not on the registry yet: try again in a few minutes;
- npm is missing;
- the network is down, or the fetch took over 120 seconds;
- the cache cannot be written.

The fetch uses your own npm configuration (`~/.npmrc` and the upper-case `NPM_CONFIG_*` variables). A project's `.npmrc` and lower-case `npm_config_*` variables do not reach it. If only the project's `.npmrc` names your registry, the network message gives the `NPM_CONFIG_REGISTRY=<your registry>` form to run.

## Upgrading

Nothing migrates, and nothing changes by itself:

- `follow --write` and `handover --write` write only when you run them;
- `next` and `dashboard` write nothing to the vault;
- the cache gets a `dashboard/0.30.19/` folder on the first `dashboard` run from an npm copy. It stays until you delete it, and a later version adds its own;
- the plan gate asks one more question, only where a WIP limit is set and the start would go over it;
- a vault with no person marked `left` gets no new doctor finding.

The command texts change (a new `/projectstore:follow`, plus story, status and doctor), so an installed copy needs the upgrade to get them.

From npm, from a terminal in your project:

```
npx projectstore@0.30.19 upgrade
```

Codex's registration is per machine. It gets the new follow skill and the updated story and status skills:

```
npx projectstore@0.30.19 upgrade --harness codex
```

From the git marketplace, in a Claude Code session: open `/plugin manage` and choose **Update now** on projectstore, then run `/reload-plugins` to load it. Or, from a terminal, then restart Claude Code:

```
claude plugin update projectstore@SmartAndPoint
```

The git marketplace serves main, so a copy installed or updated since these changes merged may already have them under the number 0.30.18. For it, this release changes the number.

The agents block stays v5.

## Not seen live yet, and known gaps

- The dashboard fetch from the registry. Before this release the page was never on npm, so it was checked from a packed tarball only. The first run of `npx projectstore@0.30.19 dashboard` with an empty cache is checked after the publish.
- A core running main's code from a copy that is not a checkout can still take itself for an npm copy and try the fetch. A planned story covers it.
- `follow` reads through `gh`, so it works with GitHub only. It was checked with `gh` read-only on this repository and by hand on a scratch vault, not on GitHub Enterprise.
- The dashboard's first read of one large iCloud vault once took 241 seconds; after a restart it took 36 ms. The cause is not known.
